# Migration Guide — 2.38.0 → 2.38.1: the 2FA page keeps the session token out of a script-readable cookie

**Security fix. Every project with two-factor sign-in needs it.**

In the cookie mode, the default, nest-server answers the second factor (`verifyTotp`,
`verifyBackupCode`) with `{ token, user }`. `token` is Better Auth's opaque session token: the
credential the httpOnly session cookie exists to keep away from scripts. `app/pages/auth/2fa.vue`
stored that token in `jwtToken`, which nuxt-extensions keeps in the cookie `lt-jwt-token` (or
`<prefix>-jwt-token`). That cookie is readable by JavaScript and lives for seven days. A single
XSS on any page of the app was therefore enough to read the session token of every user who had
signed in with 2FA, and to use it. The fallback through `getSession()` did the same with the
session's token.

2.38.1 stores a token from an answer only when it is a JWT, by the same test as `isJwtShaped` in
nest-server: three parts and a JSON header (`eyJ`). An opaque session token never passes it. The
page then signs the user in on the session cookie (`setUser(user, 'cookie')`) and asks
`/iam/token` for a JWT (`switchToJwtMode()`). In the JWT mode the API answers with a JWT, and the
page signs in with it (`setUser(user, 'jwt')`). A session token an earlier version stored in
`lt-jwt-token` is removed once the user completes the second factor again. nuxt-extensions 1.25.1
applies the same rule to its own sign-in helpers.

| Project                                      | What to do         |
| -------------------------------------------- | ------------------ |
| Uses the 2FA page (`app/pages/auth/2fa.vue`) | Steps 1 and 2, now |
| Has no two-factor sign-in                    | Nothing            |

## A limit under nest-server 12.6.0 in the JWT mode

The JWT mode is the top-level `cookies: false` of the nest-server config (`NSC__COOKIES=false`).
There, nest-server 12.6.0 still answers the second factor with the raw session token, not with a
JWT. The fixed page does not store it, and without a session cookie `/iam/token` has nothing to
convert either, so the 2FA sign-in fails in the pure JWT mode until the API runs nest-server
12.6.1, which answers with a JWT. The cookie mode is not affected. A project in the JWT mode with
2FA users takes 2.38.1 together with nest-server 12.6.1; storing the raw token again is not a way
out, because it is exactly the leak this release closes.

## What changed

| Area         | Change                                                                                                                                                                                                                                        |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **2FA page** | `onSubmit` stores a token from the answer or from `getSession()` only when it is a JWT; otherwise it signs in with `setUser(user, 'cookie')` and `switchToJwtMode()`. A non-JWT `lt-jwt-token` is removed                                     |
| **Tests**    | New `tests/unit/pages/auth-2fa.test.ts`; step 5 of `tests/e2e/auth-lifecycle.spec.ts` checks that every `*jwt-token` cookie holds a JWT, never the session token                                                                              |
| **E2E docs** | `docs/e2e-auth.md` names the real mode switch (top-level `cookies`, `NSC__COOKIES`); `features.jwt` only reports the JWT plugin. `auth-lifecycle.spec.ts` checks the mode declared in `E2E_EXPECT_AUTH_MODE` against the API's session cookie |

### 2. Take over the tests

Copy `tests/unit/pages/auth-2fa.test.ts`. It runs in every project and fails against the old page.

Add the check to step 5 of `tests/e2e/auth-lifecycle.spec.ts`, after the line that waits for the
user's address on `/app`:

```ts
const cookies = await page.context().cookies();
const sessionToken = decodeURIComponent(cookies.find((cookie) => cookie.name.endsWith('session_token'))?.value ?? '').split('.')[0];
for (const cookie of cookies.filter((candidate) => candidate.name.endsWith('jwt-token'))) {
  expect(cookie.value, `${cookie.name} must hold a JWT, not the session token`).toMatch(/^eyJ[\w-]*\.[\w-]+\.[\w-]+$/);
  expect(cookie.value).not.toBe(sessionToken);
}
```

Against nest-server 12.6.0 this check fails on the old page and passes on the fixed one, which is
how it was verified for this release. A project that also copies the template's
`auth-lifecycle.spec.ts` as a whole gets the `E2E_EXPECT_AUTH_MODE` check with it; see
`docs/e2e-auth.md`, "Configuration scenarios".

### A session token already stored in a browser

The old page wrote the session token into `lt-jwt-token`, and the cookie lives for seven days after
it was written. With 2.38.1 the page removes it the next time the user completes the second
factor; otherwise it expires on its own, and nuxt-extensions 1.25.1 removes such a value on its
own. In your own browser, and in any test browser, delete an `lt-jwt-token` (or
`<prefix>-jwt-token`) whose value is not a JWT (`eyJ….….…`) in the developer tools under
Application → Cookies.

## Check it

Sign in with a 2FA account in the cookie mode and open the developer tools under Application →
Cookies. `lt-jwt-token` is either missing or holds a JWT that starts with `eyJ` and has three parts
separated by dots. It is never the value in front of the dot in the `…session_token` cookie.

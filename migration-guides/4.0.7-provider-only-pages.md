# Migration Guide: 4.0.7 — the other pages follow `/iam/features` too

Since 4.0.6 the login page offers only the sign-in methods `GET /iam/features` reports. An API that signs
in through social providers alone (`betterAuth.emailAndPassword.enabled: false`, nest-server 12.11.0+)
still found four places that assumed a password:

- `/app/settings/security` offered "2FA aktivieren" and "Passkey hinzufügen". The API reports
  `twoFactor: false` and `passkey: false` there, the endpoints answer 404, and every click failed. The
  page also asked for the passkey list on every visit and logged the 404.
- `/auth/forgot-password` showed its form. There is no password to reset, and the request fails.
- `?error=account_not_linked` after a provider sign-in asked to sign in "wie bisher", which pointed at
  a password nobody can use there.
- `/auth/setup` created the first admin with a password without saying how that admin signs in.

Since 4.0.7:

| Page                        | With `false`                                                                                                         |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `/app/settings/security`    | `twoFactor`: no 2FA section; `passkey`: no passkey section and no list request; neither left: a hint                 |
| `/auth/forgot-password`     | `emailAndPassword`: to the login with the toast "Passwort zurücksetzen nicht verfügbar", replacing the history entry |
| `?error=account_not_linked` | `emailAndPassword`: points at the provider used before or the administration                                         |
| `/auth/setup`               | `emailAndPassword`: the form stays, with a hint how the admin signs in                                               |

Only an explicit `false` changes a page: an API before 12.11.0 does not report the fields, and
everything stays as it was.

**The first admin of a provider-only API.** `POST /system-setup/init` still wants a password. The admin
signs in through a provider whose account carries the same address, and Better Auth 1.7 links that account
to the admin on the first sign-in only when the provider reports the address as verified, and the admin's
own address is verified (the system setup sets it). GitHub reports the verified flag of the address.
Microsoft Entra ID reports it only with the optional ID token claim `verified_primary_email`: add it in
the app registration under "Token configuration" → "Add optional claim" → ID. Without it the admin's
first sign-in ends with `account_not_linked`.

Do not list the provider in `betterAuth.options.account.accountLinking.trustedProviders` to get there. It
skips the provider's check: Better Auth then links whatever address the provider names, verified or not,
and an Entra tenant admin who sets a user's `mail` to the admin's address signs in as the admin
("nOAuth"; Microsoft warns about apps that identify users by the e-mail claim).

| Project                                                                 | What to do                        |
| ----------------------------------------------------------------------- | --------------------------------- |
| Signs in through providers alone, or will (API on nest-server 12.11.0+) | Steps 1 to 4, then 5              |
| Has 2FA or passkeys switched off in the API                             | Step 1                            |
| Any other                                                               | Nothing; the steps change nothing |

No dependency changes. The pages work with every nuxt-extensions 4.x.

## Upgrade steps (existing project)

In an `lt fullstack` monorepo, the steps happen in `projects/app/`. Where a file is still the starter's,
take it over; otherwise apply the changes by hand.

### 1. `app/pages/app/settings/security.vue`

```ts
const { features, fetchFeatures, is2FAEnabled, registerPasskey, setUser, user } = useLtAuth();

// Fetched during SSR, as on register.vue, so the server HTML already leaves the sections out.
if (import.meta.server) {
  await fetchFeatures();
}

const twoFactorAvailable = computed<boolean>(() => features.value.twoFactor !== false);
const passkeyAvailable = computed<boolean>(() => features.value.passkey !== false);
const providersOnly = computed<boolean>(() => features.value.emailAndPassword === false);
```

`onMounted` calls `loadPasskeys()` only while `passkeyAvailable`. The 2FA card gets
`v-if="twoFactorAvailable"`, the passkey card `v-if="passkeyAvailable"`, and above them:

```vue
<UAlert
  v-if="!twoFactorAvailable && !passkeyAvailable"
  color="neutral"
  variant="subtle"
  icon="i-lucide-info"
  title="Keine weiteren Anmeldefaktoren"
  :description="
    providersOnly
      ? 'Du meldest dich über einen externen Anbieter an. Zwei-Faktor-Authentifizierung und weitere Schutzmaßnahmen richtest du in deinem Konto bei diesem Anbieter ein.'
      : 'Zwei-Faktor-Authentifizierung und Passkeys sind für diese Anwendung nicht eingerichtet.'
  "
/>
```

The `await` makes the page's setup asynchronous. A unit test of your own that mounts the page has to
mount it inside `<Suspense>`, as `tests/unit/pages/settings-security-features.test.ts` does.

### 2. `app/pages/auth/forgot-password.vue`

After `useRuntimeConfig()`:

```ts
const toast = useToast();
const { features, fetchFeatures } = useLtAuth();

if (import.meta.server) {
  await fetchFeatures();
}

watch(
  () => features.value.emailAndPassword,
  (emailAndPassword) => {
    if (import.meta.server || emailAndPassword !== false) {
      return;
    }
    toast.add({
      color: 'warning',
      description: 'Diese Anwendung nutzt keine Anmeldung mit Passwort. Bitte melde dich über die Anmeldeseite an.',
      title: 'Passwort zurücksetzen nicht verfügbar',
    });
    navigateTo('/auth/login', { replace: true });
  },
  { immediate: true },
);
```

Keep the redirect on the client, as on `register.vue`: a redirect from the server is a bare 302 without
a payload, and the toast would be lost.

### 3. `app/utils/social-sign-in.ts` and `app/pages/auth/login.vue`

`socialSignInError(code, context)` takes a second argument, `{ passwordSignIn?: boolean }`, and returns
for `account_not_linked` with `passwordSignIn: false`:

> Für diese E-Mail-Adresse gibt es bereits ein Konto, das nicht mit diesem Anbieter verbunden ist. Bitte
> melde dich über den Anbieter an, den du bisher genutzt hast, oder wende dich an die Administration.

Every other code and every other call keeps its text. In `login.vue` the code goes into state and the
message is computed from it, so it follows the features:

```ts
const socialErrorCode = ref<unknown>(route.query.error);
const socialError = computed<null | SocialSignInError>(() => socialSignInError(socialErrorCode.value, { passwordSignIn: passwordSignIn.value }));
```

Every `socialError.value = null` becomes `socialErrorCode.value = null`.

### 4. `app/pages/auth/setup.vue`

```ts
const { features } = useLtAuth();
const providersOnly = computed<boolean>(() => features.value.emailAndPassword === false);
```

In the `#description` slot of the form, after the paragraph:

```vue
<UAlert v-if="providersOnly" color="info" variant="subtle" icon="i-lucide-info" title="Anmeldung nur über einen Anbieter" class="mt-4 text-left">
  <template #description>
    <p>Gib die E-Mail-Adresse an, die das Konto des Administrators beim Anbieter hat. Das Passwort verlangt die Einrichtung, zum Anmelden dient es nicht.</p>
    <p class="mt-2 wrap-anywhere">
      Die API verbindet beide Konten bei der ersten Anmeldung, wenn der Anbieter die Adresse als bestätigt meldet. GitHub tut das, Microsoft Entra ID
      mit dem optionalen Claim <code>verified_primary_email</code> in der App-Registrierung.
    </p>
  </template>
</UAlert>
```

**The test pins it.** `tests/unit/pages/auth-setup.test.ts` provides the page's auto-imports as globals,
and the page now calls `useLtAuth()`. Take the 4.0.7 file over, or add to its `mountPage`:

```ts
vi.stubGlobal('useLtAuth', () => ({ features: ref({}) }));
```

Without it the tests that mount the page fail with `useLtAuth is not defined`.

### 5. Optional: the tests

- `tests/unit/pages/settings-security-features.test.ts`: new, copy it.
- `tests/unit/pages/auth-setup.test.ts`, `tests/unit/pages/auth-login-social.test.ts`,
  `tests/unit/utils/social-sign-in.test.ts`: take over the 4.0.7 files for the provider-only cases.
- `tests/e2e/auth-sign-in-methods.spec.ts`: the new test for `/auth/forgot-password` runs with
  `E2E_SIGN_IN_CASE=providers-only` against an API that signs in through a provider alone (see the
  4.0.6 guide `4.0.6-sign-in-methods-from-features.md`, step 3).

## Check it

```bash
pnpm run check
```

With the API signing in through a provider alone: `/auth/forgot-password` goes to the login with
"Passwort zurücksetzen nicht verfügbar", `/auth/setup` on an empty database shows the hint above the
form, and a signed-in user sees only "Kontoinformationen" and the hint on `/app/settings/security`.

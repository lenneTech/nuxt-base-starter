# Migration Guide — 2.10.x → 2.11.0

Version 2.11.0 reworks the Docker story of the starter: the hand-rolled dev
container is gone, and the production `Dockerfile` is now built from the
**monorepo root** with runtime commit-SHA injection. For greenfield projects
created with a current `lt fullstack init` this is fully automatic — no action
required. For **forks of the 2.10.x starter** with their own CI/Docker wiring,
follow the steps below.

## What changed

| Area                  | Change                                                                                                                                                                                                                                                                                     |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Removed**           | `Dockerfile.dev` + `docker-entrypoint.sh` — the containerized dev workflow is replaced by `lt dev up`                                                                                                                                                                                      |
| **Build context**     | Production `Dockerfile` now expects the **monorepo root** as build context (was: the app directory). It `COPY`s `projects/app/` and builds with `cd projects/app && pnpm run build` (name-agnostic; `pnpm --filter app` silently no-ops because the package is named `nuxt-base-template`) |
| **Build identity**    | Commit SHA moved from a **build-time** bake (`APP_VERSION_COMMIT` builder ARG → `runtimeConfig.public`) to a **runtime** env (`NUXT_PUBLIC_APP_COMMIT`). Keeps the expensive `nuxt build` layer cacheable across commits                                                                   |
| **New build-arg**     | `NUXT_PUBLIC_APP_ENV` is now a **builder** ARG that gates the `./docs` layer + landing-page dev card + bug.lt reporter into staging images (build-frozen)                                                                                                                                  |
| **Runtime hardening** | `Dockerfile` runner pins `ENV HOST=0.0.0.0 PORT=3000` and adds a `HEALTHCHECK` (busybox `wget` on `/`)                                                                                                                                                                                     |
| **.dockerignore**     | Switched to `**/`-globs (monorepo-root-context resolution) and now excludes `**/.env`, `**/.claude`, `**/.husky`, `.pnpm-store`                                                                                                                                                            |
| **CI**                | `.github/workflows/test.yml` build job now boot-tests the built `.output` via `scripts/check-server-start.sh`                                                                                                                                                                              |
| **Config**            | `nuxt.config.ts` gains build-frozen `appConfig.devBuild` + `runtimeConfig.public.appEnv`; the `ogImage.renderer: 'chromium'` block was removed (Satori default — no Chromium binary needed)                                                                                                |
| **Dependencies**      | `@lenne.tech/nuxt-extensions` `1.8.1 → 1.8.3`; `@lenne.tech/bug.lt` pinned `latest → 1.6.9`; `pinia` declared as an explicit direct dependency                                                                                                                                             |

## Why the build-context change

The starter now mirrors `projects/api/Dockerfile`: both build from the monorepo
root so `pnpm` can resolve the workspace. Docker only reads the **context-root**
`.dockerignore`, so the app's `.dockerignore` uses `**/`-globs to stay effective
both standalone and when copied to `projects/app/`. Image safety does not depend
on that file — the builder only `COPY`s manifests + `projects/app/`, and the
`RUN rm -rf projects/app/.env .output .nuxt` is a second guard so a developer's
local `.env` can never be baked into the bundle.

## Upgrade steps (existing 2.10.x fork)

### 1. Remove the dev-Docker files

```bash
cd nuxt-base-template
git rm Dockerfile.dev docker-entrypoint.sh
```

Local development now runs via `lt dev up` (serves app + API behind stable HTTPS
URLs with shared cookie domain) — see the README "Local Development (Parallel
Projects)" section. If you relied on the old container, replace:

```bash
# OLD — no longer works
docker build -f Dockerfile.dev -t nuxt-app-dev .
docker run -p 3001:3001 -v $(pwd):/app nuxt-app-dev

# NEW
lt dev up          # from inside the lt workspace
```

### 2. Adopt the new production Dockerfile

Copy the new `nuxt-base-template/Dockerfile` and `.dockerignore` over your fork's
versions. Then update the **build command** in your pipeline — the context is now
the monorepo root, not the app directory:

```bash
# OLD — context = app directory
docker build -f Dockerfile --build-arg APP_VERSION_COMMIT=$CI_COMMIT_SHA .

# NEW — context = monorepo root, -f points at the app Dockerfile
docker build -f projects/app/Dockerfile --build-arg APP_VERSION_COMMIT=$CI_COMMIT_SHA .
```

`lt-monorepo/docker-compose.yml` already passes `APP_VERSION_COMMIT`. Ensure the
**monorepo root ships a `.dockerignore`** — it is the only one Docker reads in a
root-context build (build-context size; image safety is already covered by the
scoped `COPY`s).

### 3. Ship dev surfaces to staging (optional)

To include the `./docs` layer + dev card + bug.lt reporter in a **staging** image,
pass the builder ARG at build time:

```bash
docker build -f projects/app/Dockerfile \
  --build-arg NUXT_PUBLIC_APP_ENV=development \
  --build-arg APP_VERSION_COMMIT=$CI_COMMIT_SHA .
```

Leave it unset for production — it resolves to `production`, and the dev surfaces
are never built. A running container **cannot** re-enable them; they are frozen at
`nuxt build` time via `appConfig.devBuild`.

### 4. Commit SHA is now runtime, not build-time

The commit surfaces under `/app/admin/system` exactly as before, but it is now
applied on boot from `NUXT_PUBLIC_APP_COMMIT` (Nitro overlays every `NUXT_PUBLIC_*`
onto `runtimeConfig.public`). The Dockerfile maps the `APP_VERSION_COMMIT` runner
ARG to it. No `nuxt build` rebuild is needed to change the reported commit — and
the build layer stays cacheable across commits. If your deployment injected the
SHA some other way at build time, drop that and rely on the runtime env.

### 5. Ensure `NUXT_API_URL` is set in production

The built server never reads `.env`. Without an API URL the SSR data layer retries
forever and can exhaust the heap on the first request. Make sure your deploy config
sets `NUXT_API_URL` (and `NUXT_PUBLIC_API_URL`) — this is not new, but the smoke
test in `check-server-start.sh` now makes the failure mode explicit.

## Rollback

This change is confined to Docker/CI/config files and two doc updates. To roll
back, restore the previous `Dockerfile`, `.dockerignore`, `Dockerfile.dev`,
`docker-entrypoint.sh`, `.github/workflows/test.yml`, and the `nuxt.config.ts`
`ogImage`/`appConfig` hunks from the 2.10.x tag. No data migration, no schema
change, no runtime state is involved.

# Migration Guide: 4.0.4 — nuxt-extensions 4.0.4, Nuxt UI 4.13.0 and tooling

The template moves to `@lenne.tech/nuxt-extensions` 4.0.4 and `@nuxt/ui` 4.13.0. nuxt-extensions
4.0.4 asks nothing of a project. Against an API that reports `jwt: false` in `GET /iam/features`
(nest-server with `betterAuth.jwt: false`), `useLtAuth()` and `ltAuthFetch` no longer ask
`/iam/token` for a JWT, so the one or two 404s with a console error on every page load of a
cookie-only project are gone.

| Project                                       | What to do       |
| --------------------------------------------- | ---------------- |
| Every project                                 | Steps 1 and 2    |
| Carries `'esbuild@<0.28.1'` under `overrides` | Step 3, optional |
| Raised `@vueuse/nuxt` to 15 on its own        | Also step 4      |

Unchanged on purpose: better-auth and `@better-auth/passkey` stay on 1.7.19, in step with the API.
TypeScript stays on 6.0.3: vue-tsc 3.3.14, the newest release, loads `typescript/lib/tsc`, which
TypeScript 7 no longer exports, and `@volar/typescript` 2.4.30 requires `typescript <7`.
`@vueuse/nuxt` stays on 14.4.0 (step 4).

## Upgrade steps (existing project)

In an `lt fullstack` monorepo, `pnpm add` and `pnpm update` run in `projects/app/`. The `overrides`
live in the root `pnpm-workspace.yaml`, where `lt` hoisted them.

### 1. nuxt-extensions and Nuxt UI

```bash
pnpm add -E @lenne.tech/nuxt-extensions@4.0.4 @nuxt/ui@4.13.0
```

If the project carries the `'@nuxt/ui@<4.8.1'` override, raise its target to `4.13.0` in the same
change. It also lifts `@lenne.tech/bug.lt`'s pinned `@nuxt/ui` 4.2.1, and with a different target the
tree holds two copies of `@nuxt/ui`. `@nuxt/ui` 4.13.0 still pins reka-ui 2.11.0, so the reka-ui
patch from starter 2.33.1 keeps applying.

Nuxt UI 4.13.0 has no breaking change. These fixes change behaviour; the template meets none of
them, but check your own code:

- `UButton` without `to` or `href` no longer renders through `ULink` (nuxt/ui#7221).
- `UTable` hides its empty state while `loading` is set and marks itself `aria-busy`
  (nuxt/ui#7360, #7368). A test that expects the empty text during loading has to wait for the data.
- The `compare` util matches `null` only with `null` (nuxt/ui#7441). This affects `USelect`,
  `USelectMenu` and `UInputMenu` with `null` among the values.

### 2. Tooling

```bash
pnpm add -E -D oxlint-tsgolint@7.0.2008 vue@3.5.46 lint-staged@17.6.2 mongodb@7.9.1 @iconify-json/lucide@1.2.158
pnpm dedupe
pnpm why vue @vue/compiler-sfc    # 3.5.46 only
```

Run the dedupe: without it, `@vue/compiler-*` 3.5.45 stays in the lockfile next to `vue` 3.5.46,
held by `@vue-macros/common`. `pnpm update --depth Infinity` did not move it in the measurement.

The template's `packageManager` is pnpm 11.29.0, which carries several security fixes. Copy the
`packageManager` line, hash included, from the template into every `package.json` that carries one
(in an `lt fullstack` monorepo also the root and the api). Docker and CI derive pnpm from that field.

### 3. Optional: drop the esbuild override

The template no longer carries `'esbuild@<0.28.1': 0.28.2`. nitropack 2.13.6 requests esbuild
`^0.28.2` itself, and every other consumer takes that copy, so a fresh resolve holds esbuild 0.28.2
with or without the entry. Keeping it does no harm: `check-overrides` reports it as `UNUSED` at
most and does not fail.

To drop it, delete the entry with its comment, then:

```bash
pnpm install
pnpm why -r esbuild    # nothing below 0.28.1
pnpm audit
```

In a monorepo whose api has an esbuild consumer of its own, keep the entry while `pnpm why -r
esbuild` shows a version below 0.28.1 without it.

### 4. `@vueuse/nuxt` stays on 14

A project that raised `@vueuse/nuxt` to 15 goes back to 14.4.0:

```bash
pnpm add -E @vueuse/nuxt@14.4.0
```

`@nuxt/ui` 4.13.0 still requires `@vueuse/core` ^14.4.0, and that is the copy the app imports. With
`@vueuse/nuxt` 15 the auto-imports follow version 15 while the code that runs is 14.4.0: in the
measurement, a page using `useLiveAnnouncer`, new in 15, passed the type check as `any` and broke
`nuxt build` with `MISSING_EXPORT`, and `templateRef`, which 15 dropped from the auto-imports, failed
the type check with `TS2304`. Move to 15 once `@nuxt/ui` does.

# Migration Guide — 2.33.4 → 2.34.0

2.34.0 makes the AI pages optional and adds an MCP confirmation switch.

- **AI pages only while the API runs its AI module.** nest-server-starter leaves the module off. The
  app now asks the API (`GET /ai/status`, nest-server 12.3.1, read with `useLtAiStatus()` from
  `@lenne.tech/nuxt-extensions` 1.23.0) and shows the AI navigation, the AI routes and the admin's AI
  cards only while the module runs. An AI route opened while it is off goes to `/app`.
- **MCP confirmation switch.** Over MCP (Claude Desktop, Claude Code and other clients), nest-server
  asks the user before a destructive tool runs. Each user may switch that question off for
  themselves, like a "bypass permissions" mode. The switch sits on `/app/settings/ai` and appears
  only while the API runs an MCP server.

**Steps 1 and 2 are required for every project**: better-auth moves to 1.7.16 across the stack,
together with the API (nest-server 12.3.1), which closes the better-auth advisories published on
2026-11-03 (among them unverified OAuth emails treated as verified, passkey checks without origin,
and revoked sessions that stay valid in the cookie cache); nuxt-extensions 1.23.0 requires it.
Steps 3 to 5 are for projects with the AI pages. The pages live in the project's own code, so a
template update does not bring them. Step 6 is a cleanup for every project that took the 2.33.4
overrides, step 7 for every project that prints a `NUXT_B7002` warning on `nuxt dev`.

## What the switch does and does not affect

- Off: an MCP client acting for this user runs destructive tools without asking first.
- Unaffected: the in-app chat, other users, each tool's own `authorize()` check, and the admin's
  `deny` / `ask` tool rules.
- The card appears only while the API runs an MCP server (`ai.mcp`, reported as `mcp: true` by
  `GET /ai/status`). Without one the switch would change a setting nothing reads.

## Steps

### 1. Required: better-auth 1.7.16, together with the API

better-auth is one protocol with two ends, so the app moves when the API does (nest-server 12.3.1),
never alone:

```bash
pnpm add -E better-auth@1.7.16 @better-auth/passkey@1.7.16
```

The fixes sit on the server side, in the API: GHSA-9hm7-xhfp-cx58 (OAuth email), GHSA-gv75-j3v8-3crm
(passkey origin and user verification), GHSA-hwq2-v29r-p69r (email-change links) and
GHSA-fvxx-76fc-893x (revoked sessions), plus better-call 1.4.5 (GHSA-23w8-wx9r-vm57, which
better-auth's own handler does not reach). This app uses `better-auth/vue` and
`better-auth/client/plugins` only, so it moves for the lock-step: an lt-monorepo's consistency check
fails while API and app resolve different better-auth versions.

After the API is on 12.3.1, passkey sign-in checks the origin. If passkey sign-in fails with
`ORIGIN_NOT_CONFIGURED`, the API's passkey configuration lacks the app's origin; that is fixed in
the API, not here.

Before 2026-11-04 21:24 UTC pnpm's one-day gate still blocks these versions. The template carries ten
exact entries in `minimumReleaseAgeExclude` for that window (see its `pnpm-workspace.yaml`); copy them
only if you update before then, and remove them afterwards. Later, no entry is needed.

### 2. Required: raise nuxt-extensions

```bash
pnpm add -E @lenne.tech/nuxt-extensions@1.23.0
```

1.23.0 requires better-auth 1.7.16 (step 1) and brings `useLtAiSettings()` and `useLtAiStatus()`.

### 3. AI pages only while the API runs its AI module

**Update the API to nest-server 12.3.1 first.** An older API answers `GET /ai/status` with 404, and
the app then hides the AI pages although the module runs. The pages also need the module itself:
nest-server-starter has no `ai` block, so set one in `config.env.ts` or `NSC__AI__ENCRYPTION_SECRET`.

Take from the template:

- [`app/utils/ai-routes.ts`](https://github.com/lenneTech/nuxt-base-starter/blob/main/nuxt-base-template/app/utils/ai-routes.ts)
  and [`app/middleware/ai.global.ts`](https://github.com/lenneTech/nuxt-base-starter/blob/main/nuxt-base-template/app/middleware/ai.global.ts),
  as they are; add your own AI routes to `isAiRoute()`,
- in `app/layouts/default.vue`: `useLtAiStatus()`, `loadAiStatus()` in `onMounted`, and the AI
  links only while `aiEnabled`,
- in `app/pages/app/admin/index.vue`: the `cards` filter on `aiEnabled` and `isAiRoute()`.

### 4. Add the MCP card to `app/pages/app/settings/ai.vue`

Take these pieces from the template's
[`ai.vue`](https://github.com/lenneTech/nuxt-base-starter/blob/main/nuxt-base-template/app/pages/app/settings/ai.vue):

- the `useLtAiSettings()`, `useLtErrorTranslation()` and `useLtAiStatus()` lines, and
  `loadSettings()` in `onMounted` (only while `mcp`),
- the function `setMcpConfirmation()`,
- the `<!-- MCP confirmation -->` card with `v-if="mcp"`.

The card appears only while the API runs an MCP server (`ai.mcp`, or `NSC__AI__MCP__ENABLED=true`).
If the page was customised, adapt the card to it rather than replacing the file.

### 5. Optional: take the tests

Copy the unit tests (`tests/unit/utils/ai-routes.test.ts`, `tests/unit/middleware/ai-global.test.ts`,
`tests/unit/pages/settings-ai-mcp-confirmation.test.ts`) and the two E2E specs
(`tests/e2e/ai-visibility.spec.ts`, `tests/e2e/ai-settings-mcp-confirmation.spec.ts`). For the E2E
specs, add `'aiUserSettings'` to `COLLECTIONS` in `tests/e2e/helpers/auth-backend.ts`.

`ai-visibility` checks whichever state the API is in. The MCP spec needs the module and its MCP
server:

```bash
NSC__AI__ENCRYPTION_SECRET=<any 32 characters>
NSC__AI__MCP__ENABLED=true
```

Without them the MCP spec skips. Set them in the CI job that runs the suite as well (job level, so
the API and Playwright both see them): a run that has them fails instead of skipping, so a lost
variable or an API below nest-server 12.3.1 shows up as red.

### 6. Optional: drop the archiver-utils override

Projects that copied the four entries of 2.33.4 step 1 can remove `'archiver-utils>glob@<14.0.2'` and
its comment from `pnpm-workspace.yaml` once they resolve nitropack 2.13.6 or later (nuxt 4.6.4 brings
it). Check first that nothing pulls archiver-utils any more; in a monorepo, run it at the root so
every project counts:

```bash
pnpm why archiver-utils   # must print nothing
```

Then run `pnpm install`, so the lockfile drops the override as well. Without it, the next
`pnpm install --frozen-lockfile` (CI, the start of `check`) stops with
`ERR_PNPM_LOCKFILE_CONFIG_MISMATCH`.

The `check-overrides.mjs` copied before 2.34.0 does not point this out: it looks only at the target
package (glob, still in the tree), not at the consumer in front of the `>`. The 2.34.0 copy, ported
from nest-server, warns about every override "that changes nothing in the resolved tree": a parent
that left the tree, a parent that no longer depends on the package, or a selector that matches no
version any more. Take `scripts/check-overrides.mjs` and `tests/unit/check-overrides.guard.spec.ts`
from the template to get that check. Run it as `pnpm run check:overrides`: the warning names the
entry and its reason, while `pnpm run check` only shows the count of checked overrides and passes.

In an lt fullstack monorepo the overrides live at the root, and the root's own guard
(`scripts/check-overrides.mjs` from lt-monorepo) checks them. lt-monorepo 3.17.1 has the same check:
copy its `scripts/check-overrides.mjs` and `scripts/check-overrides.test.ts` to the monorepo root,
then `pnpm run check:overrides` there names the entry. An older copy looks at the target only, so
`pnpm why archiver-utils` at the root is the test with it.

### 7. Optional: silence the Plausible warning on `nuxt dev`

Every `nuxt dev` start prints:

```
WARN  [NUXT_B7002] Some vite.optimizeDeps.include entries could not be resolved: @plausible-analytics/tracker.
```

`@nuxtjs/plausible` 4.0.0 adds its tracker to `vite.optimizeDeps.include` by bare name, and under
pnpm the tracker is only a dependency of the module, not of the project, so the entry resolves to
nothing (nuxt-modules/plausible#52, open). Declare it at the version the module resolves:

```bash
pnpm why @plausible-analytics/tracker      # e.g. 0.4.7
pnpm add -E @plausible-analytics/tracker@0.4.7
```

The entry then finds the same copy the module's client plugin imports, so the tracker is pre-bundled
once and the warning is gone. `tests/unit/optimize-deps-contract.test.ts` gains a check that every
`include` entry, the modules' own included, resolves from the project root.

## Troubleshooting

| Symptom                                                                          | Cause and fix                                                                                                                                                                         |
| -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| No AI links, and `/app/ai` goes to `/app`, although the API runs its AI module   | `GET /ai/status` does not answer 200: the API runs below nest-server 12.3.1 (404, step 3), or the request fails (network, a proxy answering HTML). `useLtAiStatus().error` says which |
| No MCP card on `/app/settings/ai`                                                | The API runs no MCP server: `GET /ai/status` reports `mcp: false`. Set `ai.mcp` or `NSC__AI__MCP__ENABLED=true` in the API                                                            |
| No switch, only "Die Einstellung ist gerade nicht verfügbar."                    | `GET /ai/settings` fails although the status says MCP runs, for example an expired session. Reload after signing in again                                                             |
| Switch locked, "Die Einstellung ist vom Server festgelegt …"                     | Intended: the API sets `ai.mcp.confirmation.enforced`. Only the server configuration changes the value                                                                                |
| `typecheck` fails with `Cannot find name 'useLtAiStatus'` or `'useLtAiSettings'` | `@lenne.tech/nuxt-extensions` is below 1.23.0 (step 2)                                                                                                                                |

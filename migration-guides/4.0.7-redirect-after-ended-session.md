# Migration Guide: 4.0.7 — nuxt-extensions 4.0.7, the way to the login after an ended session

The template moves to `@lenne.tech/nuxt-extensions` 4.0.7. It asks nothing of the project's code and
fixes a regression of 4.0.6:

- Since 4.0.6, `validateSession()` signs out a cached user once a direct `get-session` confirms that
  the API has no session for them. The 401 interceptor then ignored the next 401, because nobody was
  signed in any more. The page showed the visitor signed out, every request failed, and no redirect
  came until the visitor navigated somewhere.
- 4.0.7 hands that 401 to the interceptor again: it checks the session and sends the browser to
  `/auth/login?redirect=<the page>`, as up to 4.0.5.

**Who was affected:** an app that stays in cookie mode, above all against an API without JWT
(`/iam/features` reports `jwt: false`, nest-server with `betterAuth.jwt.enabled: false`). With JWT on,
the app keeps a JWT after the first page load, `validateSession()` keeps the user while one is stored,
and the redirect came in 4.0.6 too (measured with the template against nest-server-starter 12.11.2).

| Project                                                | What to do       |
| ------------------------------------------------------ | ---------------- |
| Every project                                          | Step 1           |
| Wants the E2E check, above all with an API without JWT | Step 2, optional |

## Upgrade steps (existing project)

In an `lt fullstack` monorepo, `pnpm add` runs in `projects/app/`.

### 1. nuxt-extensions

```bash
pnpm add -E @lenne.tech/nuxt-extensions@4.0.7
pnpm audit         # No known vulnerabilities found
pnpm peers check   # No peer dependency issues found
pnpm run check
```

No other package moves; the lockfile changes in `@lenne.tech/nuxt-extensions` alone.

### 2. Optional: the E2E check

Copy `tests/e2e/auth-session-ended.spec.ts`. It registers a user, ends the session on the API
(`POST /iam/sign-out` with the browser's session cookie, from a request context of its own), reloads
`/app` and expects the next protected request to lead to `/auth/login?redirect=%2Fapp`. Against an API
without JWT it also checks that the page shows the visitor signed out in between.

- It needs `tests/e2e/helpers/auth-backend.ts` with `Features.jwt` (in the template since 2.x) and the
  API log for the verification token, as `auth-lifecycle.spec.ts` does (`docs/e2e-auth.md`).
- In vendor mode change the import `from '@lenne.tech/nuxt-extensions/testing'` to
  `from '../../app/core/runtime/testing'`.
- Against an API without JWT, run it with `E2E_SESSION_CASE=no-jwt`: the spec then fails instead of
  passing without the decisive step when the API reports JWT on. The template's CI does that in the
  job `e2e-auth`, with a second API on :3002 started with `NSC__BETTER_AUTH__JWT__ENABLED=false`.
- Cookie mode only: with `E2E_EXPECT_AUTH_MODE=jwt` it skips.

## Check it

With an API without JWT: sign in, end the session on the API (or let it expire), reload `/app` and
start any action that sends a request. The browser lands on the login, and after signing in again it
returns to `/app`.

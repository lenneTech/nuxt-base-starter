# Migration Guide — 2.35.1 → 2.36.0: setup page and the closed HTTP init

From nest-server 12.4.0 on, the first admin can no longer be created over HTTP on a deployed
system unless that is released explicitly. `POST /system-setup/init` is closed outside the
environments `local`, `ci` and `e2e`, and `GET /system-setup/status` says so in two new fields,
`httpInitEnabled` and `httpInitTokenRequired`.

The setup page of older projects does not read these fields. On a fresh deployed system without
users it keeps showing its form, and every submit fails with 403. Because the page passed
`err.message` to `translateError`, the user only reads the transport line
`[POST] "…/system-setup/init": 403 Forbidden`.

2.36.0 shows the form only while the API takes the first admin over HTTP. Otherwise the page explains
how to set the system up through the configuration. A setup token the API asks for gets its own field.

| Project                                                     | What to do                                                                 |
| ----------------------------------------------------------- | -------------------------------------------------------------------------- |
| Pairs with nest-server 12.4.0 or newer                      | Steps 1 and 2 are required; step 4 for every deployed stage without users  |
| Still on an older nest-server                               | Steps 1 and 2 are safe now: without the new fields the page shows its form |
| Created the first admin long ago, never sets up a new stage | Steps 1 and 2 keep the page correct; nothing else changes                  |

## What changed

| Area           | Change                                                                                                                                                                                                                                                            |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Setup page** | `app/pages/auth/setup.vue` shows the form only while `needsSetup` and `httpInitEnabled` hold, the hint while the HTTP init is closed, and a token field while `httpInitTokenRequired` holds                                                                       |
| **Errors**     | A refused submit shows the backend message (`LTNS_0053` HTTP init closed, `LTNS_0054` token missing or wrong) through `translateError(err)` instead of the transport line                                                                                         |
| **Dependency** | `@lenne.tech/nuxt-extensions` 1.24.1 → 1.25.0: `useSystemSetup()` reads the two fields and sends the token as header `X-System-Setup-Token`; the setup middleware stops redirecting to the setup page while the HTTP init is closed, so the login stays reachable |
| **Tests**      | New `tests/unit/pages/auth-setup.test.ts` (every state of the page) and `tests/e2e/system-setup.spec.ts` (real API on an empty database, closed and open)                                                                                                         |
| **CI**         | The template's own e2e job starts its API twice on the empty database and creates the first admin through the form instead of a bare `POST /system-setup/init`                                                                                                    |

## Upgrade steps (existing project)

In an `lt fullstack` monorepo, steps 1 to 3 happen in `projects/app/`.

### 1. Raise nuxt-extensions

npm mode:

```bash
pnpm add -E @lenne.tech/nuxt-extensions@1.25.0
```

Vendor mode: `/lt-dev:frontend:update-nuxt-extensions-core`.

### 2. Take over the setup page

Copy `app/pages/auth/setup.vue` from the template. A project that changed its copy takes over four
parts:

- the `view` computed and the `v-if` / `v-else-if` blocks in the template that it drives,
- the token field (`tokenField`, `fields`) and the token check in `schema`,
- `token` in the `initSetup` call,
- `translateError(err)` instead of `translateError(err instanceof Error ? err.message : …)`.

No shipped test pins the old page, so nothing else turns red.

```bash
pnpm run typecheck
```

### 3. Optional: take over the tests

Copy `tests/unit/pages/auth-setup.test.ts`. It runs in every project.

`tests/e2e/system-setup.spec.ts` needs an empty database and `E2E_SETUP_CASE=closed|open`, and it
skips without that variable. Copy it only if your CI can start the API on an empty database, once
with `NSC__SYSTEM_SETUP__HTTP_INIT=false`. The e2e job in the template's `.github/workflows/test.yml`
shows the order.

### 4. Every deployed stage without users: decide how the first admin comes

With nest-server 12.4.0 the setup page of such a stage shows the hint. Choose one way:

- **The first admin through the configuration (recommended):** set
  `NSC__SYSTEM_SETUP__INITIAL_ADMIN__EMAIL`, `NSC__SYSTEM_SETUP__INITIAL_ADMIN__PASSWORD` and
  optionally `NSC__SYSTEM_SETUP__INITIAL_ADMIN__NAME` on the API and restart it. nest-server creates
  the admin at startup when no user exists.
- **The form with a setup token:** set `NSC__SYSTEM_SETUP__HTTP_INIT__TOKEN` to at least 16
  characters that are not only digits, restart the API and reload the setup page. The form then
  asks for that token.

## Check it

On a deployed stage without users and without either variable, `/auth/setup` shows the hint and no
form, and `/auth/login` opens without being sent back. Locally (`lt dev up`, empty database) the
form appears as before and creates the admin.

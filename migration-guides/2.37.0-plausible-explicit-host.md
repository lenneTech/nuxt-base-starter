# Migration Guide — 2.36.0 → 2.37.0: Plausible only with an explicit host, and nothing personal

Every project built from this template reported its pageviews to `plausible.io`, whether it used
Plausible or not. `@nuxtjs/plausible` 4.0.0 is on by default and falls back to `https://plausible.io`
without an `apiHost`. The template read the host from `NUXT_PLAUSIBLE_API_URL` at build time, and a
Docker build never sees that variable: the Dockerfile did not take it as a build arg. 2.35.0 took the
token and the e-mail address out of the query, but the requests kept going out, and with them:

- paths with record ids, tokens or codes (`/share/aB3dE`, `/orders/12345`),
- `utm_term` and `utm_content`, which often hold free text or a recipient id,
- the real `gclid` and `msclkid`,
- the full URL of an external page a visitor came from, whatever that site's policy let through.

2.37.0 starts Plausible only with an analytics host set explicitly, and sends nothing that names a
person or opens an account, whichever server receives it.

**Steps 1 to 4 are required for every project that has `@nuxtjs/plausible`**, including one that
keeps Plausible off. Without the masks, the day somebody sets a host the personal data goes out again.

| Project                                                              | What to do                                                                      |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Reports to its own Plausible server (address in config, CI or stage) | Steps 1 to 5. Afterwards the stage must still name that server (see "Check it") |
| Does not use Plausible, or reported to `plausible.io` unknowingly    | Steps 1 to 4. Afterwards nothing goes out                                       |
| Has a route with a token or code in the path (`[token]`, `[code]`)   | Step 3 as well                                                                  |
| Sends the e-mail address as `?email=` (template login and sign-up)   | Step 6                                                                          |

## What changed

| Area                          | Change                                                                                                                                                                                                                 |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Switch**                    | `plausible.enabled: false` and `apiHost: ''` when no address is set. `app/plugins/plausible.client.ts` starts the tracker only while `apiHost` holds a host                                                            |
| **Where the host comes from** | `NUXT_PLAUSIBLE_API_URL` at build time (new build arg in the Dockerfile), or `NUXT_PUBLIC_PLAUSIBLE_API_HOST` on the stage, which wins                                                                                 |
| **What Plausible sees**       | `app/utils/analytics-url.ts`: path with ids, tokens and codes masked as `:id`; only `utm_source`, `utm_medium`, `utm_campaign`, `ref`, `source` with a plain label; `gclid=1`, `msclkid=1`; referrer cut to its origin |
| **Custom events**             | Their URL and referrer pass the same masks (`transformRequest`), and so does the `url` the tracker adds to a click on an element tagged `plausible-event-name=…`. Other props do not: no e-mail, name or id in them    |
| **Automatic capture**         | Outbound links, file downloads and form submissions stay off, whatever the module options say                                                                                                                          |
| **verify-email**              | No address and no token in the URL: login and sign-up hand the address over in the history entry, the page removes both from the mail link on arrival                                                                  |

### Why the template starts the tracker itself

An address has to work on every path a project sets it, and most stages set environment variables
only at runtime. The module cannot do that safely: it reads `enabled` and `apiHost` as two separate
keys, falls back to `plausible.io` when `apiHost` is empty, and occupies the tracker's only hook
into the request (`transformRequest`) for its hostname filter. No event option reaches the referrer,
so with the module's own plugin there is no way to cut it.

So the module stays registered but idle, which keeps `useTrackEvent` and `useTrackPageview`, and the
template plugin decides at runtime: a host in `runtimeConfig.public.plausible.apiHost`, from the
build or from the stage, starts the tracker; none starts nothing. `apiHost` has to be an empty string
when no address is set, never `undefined`: `undefined` lets the module default back in, and Nitro
only applies `NUXT_PUBLIC_PLAUSIBLE_API_HOST` over a key the build wrote.

## Upgrade steps (existing project)

In an `lt fullstack` monorepo, all steps happen in `projects/app/`.

### 1. Take over the files

Copy from the template, unchanged:

- `app/utils/analytics-url.ts` — the masks. Only `PROJECT_TOKEN_SEGMENTS` is yours (step 3).
- `app/plugins/plausible.client.ts` — the tracker start.
- `app/plugins/plausible-pageviews.client.ts` — unchanged since 2.35.0; copy it if the project
  lacks it.

`tests/unit/optimize-deps-contract.test.ts` then fails with
`@plausible-analytics/tracker (imported by plugins/plausible.client.ts)`: the guard did not count the
entry @nuxtjs/plausible pushes into `optimizeDeps.include` itself. Take over the template's line in
`pre-bundles every package the client code imports`:

```ts
const covered = new Set([...optimizeDeps('include'), ...optimizeDeps('exclude'), ...moduleIncludes().map(({ entry }) => entry)]);
```

The project needs `@plausible-analytics/tracker` as a dependency (2.34.0, step 7).

### 2. Switch the module to idle

In `nuxt.config.ts`, the `plausible` block becomes:

```ts
plausible: {
  enabled: false,
  apiHost: process.env.NUXT_PLAUSIBLE_API_URL?.trim() || '',
  autoPageviews: false,
  ignoredHostnames: ['localhost'],
},
```

- **A fixed address in the config** (`apiHost: 'https://plausible.example'`): move it to the
  stage or the build (step 5) and keep the line above as it is. That keeps the copied
  `tests/unit/plugins/plausible-tracker.test.ts` (step 4) green. A project that keeps the address as
  the fallback (`apiHost: process.env.NUXT_PLAUSIBLE_API_URL?.trim() || 'https://plausible.example'`)
  has to expect it in three cases of that test: `leaves no analytics host and no running module
  without an address`, `treats an address of blanks as none` and `starts nothing with the template
  config as built without an address`. Change the expectation, not the plugin.
- **A project that already switched off with `enabled: Boolean(process.env.NUXT_PLAUSIBLE_API_URL?.trim())`**
  replaces both lines. That form ignores an address set on the stage, and with the module's plugin
  the referrer goes out in full.
- **A project that used `autoOutboundTracking`, `fileDownloads`, `formSubmissions`, `hashMode` or
  `proxy`**: those options no longer take effect. The first three report the clicked address as a
  property outside what the template masks. `hashMode` loses the fragment to `analyticsUrl`. `proxy` needs the
  module's plugin; point `NUXT_PUBLIC_PLAUSIBLE_API_HOST` at your own proxy path instead.

```bash
pnpm run typecheck
```

### 3. Mask the project's own tokens in the path

A path that resolves to one of the app's static routes keeps every segment: both plugins hand the
router to `analyticsUrl`, so `/invite/accept` stays itself next to `/invite/[code]`. In dynamic routes
and unknown paths, ids, UUIDs, numbers of five digits or more, addresses with `@`, and segments of 16
characters or more that are no lower-case slug are masked anyway. What no rule can see is a short
code behind a fixed word. Find them:

```bash
find app/pages -name '\[*' | grep -i -E 'token|code|key|secret|hash|invite'
```

For each, add the word in front to `PROJECT_TOKEN_SEGMENTS` in `app/utils/analytics-url.ts`, lower
case. `pages/einladung/[code].vue`:

```ts
const PROJECT_TOKEN_SEGMENTS: readonly string[] = ['einladung'];
```

And a case in `describe('analyticsUrl: the path')` of `tests/unit/utils/analytics-url.test.ts` (step
4), which fails without the entry:

```ts
it('masks the code of an invitation link', () => {
  expect(reported('/einladung/aB3dE')).toBe('/einladung/:id');
});
```

The template's list already covers `invite`, `koppeln`, `password-reset`, `passwort-setzen`, `reset`,
`s`, `share`, `token` and `verify`.

### 4. Take over the tests, and check custom events

Copy `tests/unit/utils/analytics-url.test.ts`, `tests/unit/plugins/plausible-tracker.test.ts` and
`tests/unit/plugins/plausible-tracker-real.test.ts`. They run unchanged in a project: they find
`pages/` under `app/`, `src/` or the root and import through `~`, which has to point at the source
directory in the project's `vitest.config.ts`.

- `analytics-url.test.ts` has one case per mask. Its case `leaves every static page of the project
  as it is` reads the project's `pages/` and checks that the router check keeps every static page.
- `plausible-tracker.test.ts` resolves the project's `nuxt.config.ts` with the real module defaults
  and fails as long as the plausible.io fallback can come back (a fixed fallback address: step 2).
- `plausible-tracker-real.test.ts` clicks a tagged link with the real tracker and checks the request.

Then search the project for `useTrackEvent`, `$plausible`, `window.plausible` and `plausible-event-`.
The URL of those events is masked now, and so is the `url` the tracker adds to a click on a tagged
link; every other prop goes out as it is. Remove every e-mail address, name or id from them, or make
it anonymous.

```bash
pnpm run test:unit
```

### 5. Pass the address to the build, or set it on the stage

Only for a project that reports to its own server. Either way works, the stage value wins:

- **On the stage** (no rebuild): `NUXT_PUBLIC_PLAUSIBLE_API_HOST=https://plausible.example`.
- **At build time**: add the build arg to the builder stage of the `Dockerfile`, next to
  `NUXT_PUBLIC_APP_ENV`, and pass it from CI with `--build-arg NUXT_PLAUSIBLE_API_URL=…`:

  ```dockerfile
  ARG NUXT_PLAUSIBLE_API_URL
  ENV NUXT_PLAUSIBLE_API_URL=$NUXT_PLAUSIBLE_API_URL
  ```

A project without its own server sets neither.

### 6. Keep the e-mail address out of the verify-email URL

Copy `app/utils/verify-email-memory.ts` and `app/pages/auth/verify-email.vue`. A project that
changed its copy takes over:

- `email` and `token` as refs read once from `route.query`, not computeds,
- `keepSecretsOutOfTheUrl()` and `rememberVerified()`, and the start of `onMounted` that calls the
  first and recalls the history entry,
- `rememberVerified()` after a successful verification, and the `remembered.verified` branch.

In `login.vue` and `register.vue` (and every project page that navigates with `query: { email }`),
the address moves into the history entry:

```ts
await navigateTo({ path: '/auth/verify-email', query: { fromRegister: 'true' }, state: verifyEmailState(payload.data.email) });
```

Copy `tests/unit/utils/verify-email-memory.test.ts`, `tests/unit/auth/no-address-in-url.spec.ts` (both
run unchanged, also on `srcDir: './src'`) and, if your CI runs the auth suite against an API,
`tests/e2e/auth-verify-email-url.spec.ts`. Vendor
mode: change the spec's import `from '@lenne.tech/nuxt-extensions/testing'` to
`from '../../app/core/runtime/testing'`, as in your other specs, or `pnpm run typecheck:tests` fails.

The link in the verification mail still carries `&email=`, because nest-server builds it. The page
removes it on arrival; in the mail and in the browser's own history it stays.

## Check it

On a deployed stage, open any page, without signing in, and read the configuration it ships in the
browser console:

```js
__NUXT__.config.public.plausible;
```

- **No address set:** `enabled: false` and `apiHost: ''`. The browser makes no request to
  `/api/event` and sets no `<link rel="preconnect">`.
- **Own server:** `apiHost: 'https://plausible.example'`, the same server as before the update. A
  pageview reaches that server, with `u` masked and `r` an origin at most.

From a shell, `curl -s https://<stage>/ | grep -o 'apiHost:"[^"]*"'` prints
`apiHost:"https:\u002F\u002Fplausible.example"` for a set address (`\u002F` is `/`) and nothing
without one. Nuxt does not write this configuration as JSON: it uses unquoted keys and moves
repeated values into variables (`apiHost:c`), so a grep for `"plausible":{` finds nothing either
way, and a set address that also appears elsewhere in the configuration can hide behind a variable
too. The console is the reliable check.

The tracker ignores `localhost` and automated browsers. To see a request in a headless browser, use
a real hostname and set `window.__plausible = true` before the page loads; without that, an empty
network log proves nothing.

# Migration Guide — 2.38.x → 4.0.0: nuxt-extensions 4.0.0 and the new version numbers

4.0.0 is the template for `@lenne.tech/nuxt-extensions` 4.0.0. From this release on, the starter
carries the version of the nuxt-extensions release it pins, and nuxt-extensions numbers its
releases like nest-server: **MAJOR** is the Nuxt major (4 = Nuxt 4), a **MINOR** is a change a
project has to migrate, a **PATCH** can be taken over as is. The switch skips numbers: the starter
goes from 2.38.5 to 4.0.0, nuxt-extensions from 1.28.0 to 4.0.0. There is no starter 3.x and no
nuxt-extensions 2.x or 3.x, and nothing in between is missing.

nuxt-extensions 4.0.0 is 1.28.0 plus three changed defaults; its own guide is
[`1.x-to-4.0.0.md`](https://github.com/lenneTech/nuxt-extensions/blob/4.0.0/migration-guides/1.x-to-4.0.0.md).
The template already works the new way, so a project made from 2.38.5 needs little more than the
update. A project on 2.38.0 to 2.38.4 applies the
[2.38.5 guide](./2.38.5-nuxt-extensions-1.28.0.md) first.

Pin the exact version, as the template does. Under the new scheme a minor is exactly the change a
project has to act on, so a caret range (`^4.0.0`) would pull one in unannounced.

| Project                                                                                | What to do    |
| -------------------------------------------------------------------------------------- | ------------- |
| Made from the starter, config as in 2.38.5                                             | Steps 1 and 5 |
| Sets no `ltExtensions.tus.defaultEndpoint`, or still `'/files/upload'`                 | Step 2        |
| Calls `getFileUrl()` / `getDownloadUrl()` / `getFileInfo()`, or builds `/files/…` URLs | Step 3        |
| Its API was not made from nest-server-starter 11.33.1+, or sets `file.downloadRoles`   | Step 3        |
| Its API registers Better Auth's `admin()` plugin and the app calls `admin.*`           | Step 4        |

An API made from nest-server-starter 11.42.13 or later needs no change. File links need nest-server
11.8.0 or later (`GET /files/id/:id`). The id an upload hands to `onSuccess` (`item.fileId`, read
from `X-File-Id`), the test of step 5 and the check at the end need nest-server 11.42.13 or later;
on an older API `fileId` stays empty, see the [2.32.0 guide](./2.32.0-tus-uploads.md). The
template's E2E runs against nest-server-starter 12.x.

## What changed

| Area           | Change                                                                                                                                 |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| **Dependency** | `@lenne.tech/nuxt-extensions` 1.28.0 → 4.0.0                                                                                           |
| **Version**    | The starter's `version` is the pinned nuxt-extensions version; `scripts/starter-version.test.mjs` in the repository root checks it     |
| **Tests**      | `tests/e2e/file-upload-link.spec.ts` uploads through the TUS endpoint and opens the file at `/files/id/:id` with and without a session |

## nuxt-extensions 4.0.0

### The default TUS endpoint is `/tus`

`ltExtensions.tus.defaultEndpoint` defaulted to `'/files/upload'`. nest-server serves TUS at `/tus`
unless its `tus.path` says otherwise, and `/files/upload` is its multipart route, so an app on
nest-server that relied on the default never completed an upload. The default is now `'/tus'`. The template has set
`'/tus'` explicitly for a long time (`tests/unit/tus-endpoint-contract.test.ts`).

### File links point at `GET /files/id/:id` on the API

`useLtFile().getFileUrl(id)` built `/files/<id>` on the app origin, which nest-server reads as a file **name**
(`GET /files/:filename`) and answers 404, and `getDownloadUrl(id)` built `/files/download/<id>`, a
route that does not exist. Both now return `<API URL>/files/id/<id>`: nest-server streams the file
there and names the download after the stored file, so `getDownloadUrl`'s `filename` argument is
ignored. `getFileInfo(id)` asks `<API URL>/files/info/<id>`. The URLs are absolute on the API, during SSR too (the public API URL), like the auth, AI and
TUS requests. `tus.resolveAgainstApi: false` keeps it relative, for an app that reaches the API
through a same-origin proxy.

The route is not public, and who may download is decided in two places. The role gate
`file.downloadRoles` says who reaches the route: nest-server's default is admins only,
nest-server-starter (11.33.1+) opens it to every signed-in user (`[S_USER]`). The per-file rule
says which file a caller gets: nest-server-starter's `FileService.checkRights()` allows the
uploader's own files and every file to an admin. nest-server's own `checkRights()` allows every
file. So never widen the role gate alone: without a per-file rule (`file.access: 'owner'`, from
nest-server 11.35.0, or a `checkRights()` of your own), every user who can sign up can download
every user's files, one guessable id after the other. The browser sends the session cookie with an
`<img>` or `<a>` only on a same-site request, which a deployment with app and API under one
registrable domain is.

### Better Auth's admin client plugin is off by default

`ltExtensions.auth.enableAdmin` defaulted to `true`. nest-server registers no `admin()` plugin, so
every `admin.*` call answered 404. The default is now `false`, and `useLtAuth()` warns once in the
console when the option is on while `/iam/features` reports no admin plugin. The template has set
`false` since 2.38.5.

## Upgrade steps (existing project)

In an `lt fullstack` monorepo, the steps happen in `projects/app/`.

### 1. Update nuxt-extensions

npm mode, in `package.json`:

```json
"@lenne.tech/nuxt-extensions": "4.0.0",
```

then `pnpm install`. Vendor mode: bring `app/core` to 4.0.0 the way your project updates its
vendored core (`app/core/VENDOR.md`).

### 2. Check the TUS endpoint

```bash
grep -n "defaultEndpoint" nuxt.config.ts
```

`'/tus'` (or the path your API's `tus.path` names) is right. No line means the new default `'/tus'`
applies, which is what nest-server serves. `'/files/upload'` reached the multipart route and never
worked for TUS there; change it to `'/tus'`. Only a backend of your own that serves TUS at
`/files/upload` keeps it.

### 3. Check file links

```bash
grep -rnE "getFileUrl|getDownloadUrl|/files/(download/)?\\$\\{" app/ server/
```

- `getFileUrl(id)` and `getDownloadUrl(id)` need no change. A link that was dead now opens the file.
- Code that put the URL behind its own API prefix (`${apiUrl}${getFileUrl(id)}`) now doubles it:
  use the return value as it is.
- A `filename` passed to `getDownloadUrl` no longer renames the download.
- A file URL your code builds itself (`/files/${id}`) has the old defect; use `getFileUrl(id)`.
- An app that reaches the API through a same-origin proxy of its own for `/files` sets
  `ltExtensions.tus.resolveAgainstApi: false`, which keeps the URLs relative, and has its proxy
  serve `/files/id/<id>`.
- Links that answered 404 now reach the API's download rules, so check them before the update
  ships. On an API made from nest-server-starter 11.33.1 or later there is nothing to do. Otherwise
  look at its `file` config and its `FileService`: `file.downloadRoles` left at the default keeps
  downloads to admins (the links answer 403 for everyone else); a widened `downloadRoles` needs
  `file.access: 'owner'` or a `checkRights()` override next to it, see the section above. The test
  in step 5 fails on an API that serves one user's file to another.

### 4. Keep the admin plugin where the API serves it

Only if your API registers Better Auth's `admin()` plugin and the app calls `useLtAuthClient().admin`:
set it on explicitly, since the default is now off:

```ts
// nuxt.config.ts → ltExtensions.auth
enableAdmin: true,
```

In a project that carries `tests/unit/auth-admin-plugin-contract.test.ts` (every project made from
2.38.5, and every project that took it over with the 2.38.5 guide), change its expectation to
`['true']` in the same commit; the test reads `nuxt.config.ts` and fails otherwise.

The template's `enableAdmin: false` (since 2.38.5) can stay; it now states the default.

### 5. Take over the test

Copy `tests/e2e/file-upload-link.spec.ts`. It registers a user, uploads a small text file through
`<API>/tus` with the requests `tus-js-client` sends, reads the stored file's id from `X-File-Id`,
and fetches `<API>/files/id/<id>`: 200 with the owner's session, refused without a session, and
refused for a second user it registers. It needs the API, the app and the API's MongoDB, see
`docs/e2e-auth.md`, and an API on nest-server 11.42.13 or later whose download rules let a signed-in
user have their own files (nest-server-starter 11.42.13 or later does). On an API that keeps
downloads to admins, the 200 for the owner fails: adapt that assertion to your rules or leave the
spec out. Vendor mode: change the spec's import
`from '@lenne.tech/nuxt-extensions/testing'` to `from '../../app/core/runtime/testing'`, as in your
other specs.

```bash
pnpm exec playwright test tests/e2e/file-upload-link.spec.ts   # needs the API with PLAYWRIGHT=true
```

## Check it

Sign in, upload a file with `TusFileUpload` (or your own upload), and open `getFileUrl(fileId)`
from its `onSuccess`: the file opens, and the network panel shows `GET <API>/files/id/<id>` with 200. Without a session the same URL is refused, and so it is for another signed-in user. The browser console shows no
`[LtAuth] ltExtensions.auth.enableAdmin is on` warning.

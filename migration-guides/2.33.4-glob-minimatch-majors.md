# Migration Guide — 2.33.3 → 2.33.4

Two moderate advisories have turned `pnpm audit` red in every project made from this template since
2026-10-30: GHSA-3g3m-2fjr-6pw4 (glob 9 – 14.0.1) and GHSA-g3hv-75wg-m249 (minimatch < 11.0.1). Both
fixes exist only in new majors (glob 14, minimatch 11, released 2026-10-27). Every consumer in the
app's tree is on its newest release and still requests the old major. All of them are build tooling:
`@vercel/nft` and `archiver` (both via nitropack), `rimraf` (devDependency). Nothing of it reaches
`.output/`.

2.33.4 lifts those four consumers across the major with scoped overrides, measured to behave the
same. It also brings both suppression guards up to nest-server 12.2.0, whose starter suppresses the
same two advisories with `auditConfig.unusableFixConsumers` declarations. `lt fullstack init`
hoists those into the monorepo root. `check-suppressions.mjs` did not know the declaration and
failed both entries as `FIX AVAILABLE`. `check-overrides.mjs` read only one consumer per declaration.

Projects created with a current `lt fullstack init` get all of it. **Existing projects do not**: the
workspace file and the scripts were copied when the project was created. Step 1 is required right
away, because `pnpm audit` fails without it. Step 5 is required as well, for a reason unrelated to
the advisories: with the current `@iconify/vue`, the browser fetches icons from Iconify's public API.

The tree then holds exactly one glob and one minimatch, and `pnpm audit` is clean. How the overrides were measured (2026-11-01): glob 14 still exports `glob`, `globSync` and `sync`, the
only calls the glob consumers make, and minimatch 11 still has `Minimatch#match`, the only API
readdir-glob uses. The old and the new major ran side by side with each consumer's exact calls and
options: 710 comparisons, 0 differences. `nuxt build` traced the identical 397 files into
`.output/server/node_modules` with and without the overrides. The full reasoning sits above the
entries in `pnpm-workspace.yaml`.

## Upgrade steps (existing project)

### 1. Add the four overrides

Copy the four entries **with their comments** from `nuxt-base-template/pnpm-workspace.yaml` of
2.33.4 into the project's `overrides:`. In an `lt fullstack` monorepo that is the root
`pnpm-workspace.yaml`, because pnpm reads overrides only there. Keep every comment directly above
its key, or a later `lt fullstack update` drops it.

```bash
pnpm install
pnpm audit
```

Do not replace them with a bare `minimatch@<11.0.1` key. In a monorepo it reaches the API's
consumers (`@nestjs/cli`, `@ts-morph/common`, `nodemon`, `@swc/cli`), and some of them call the
`makeRe()` that minimatch 11 removed.

### 2. Copy the guards with their tests

From `nuxt-base-template/` of 2.33.4, copy these seven files unchanged:

- `scripts/check-suppressions.mjs`, `scripts/check-suppressions.d.mts`, `tests/unit/check-suppressions.test.ts`
- `scripts/check-overrides.mjs`, `tests/unit/check-overrides.guard.spec.ts`
- `scripts/check.mjs`, `scripts/check.d.mts`

In a monorepo they go to `projects/app/`. If `scripts/check.mjs` carries project changes, take only
`parseSuppressionSummary` and the `retest` line in `metricSuffix`.

```bash
pnpm run check:suppressions
pnpm run check:overrides
```

### 3. Monorepo: the API's hoisted entries after step 1

The `rimraf` override applies to the API's rimraf as well, so no vulnerable glob is left anywhere in
the tree. nest-server-starter's GHSA-3g3m-2fjr-6pw4 entry then hides nothing, and both guards fail it
as `NOT IN TREE`. Delete it from `auditConfig.ignoreGhsas` together with its
`auditConfig.unusableFixConsumers` line.

The GHSA-g3hv-75wg-m249 entry stays: the API's own consumers still need minimatch 10. Its
declaration names `glob@13.0.6`, which leaves the tree with step 1, so remove that consumer from the
line. `glob@14.0.3` and `readdir-glob@1.1.3` stay out of it: they pull the patched 11.0.4, and the
guards of step 2 count only edges into an affected version. The monorepo's root guard needs the same
rule, from lt-monorepo's `scripts/check-overrides.mjs` in its release after 2026-11-02. An older
root guard counts both and fails the entry with `RE-TEST`. nest-server-starter takes the same rimraf
override and retires its glob entry in its next release, so new projects get neither line.

The monorepo root has a consumer of its own. Projects created from lt-monorepo up to 3.16.1 carry a
release tool there, `commit-and-tag-version` (older ones `standard-version`), and both pull
`dotgitignore@2.1.0 > minimatch@3.1.5`. dotgitignore 2.1.0 is its last release and calls
`minimatch.makeRe()`, which minimatch 11 removed, so no override can lift it. The hoisted declaration
does not name it, and both guards fail the entry with
`RE-TEST … dotgitignore@2.1.0 also pulls an affected package`. Choose one:

- **The project does not need `pnpm run release`:** remove the tool from the root `devDependencies`
  and the `release`, `release:minor` and `release:major` scripts, then run `pnpm install`. That takes
  the path out of the tree. Leave `.versionrc.json` and `scripts/check-wrapper-version.cjs` in place:
  without the tool they do nothing, and in projects from lt-monorepo 3.13.0 on,
  `scripts/check-wrapper-version.test.mjs` (part of `test:scripts`) still reads both. lt-monorepo
  drops the tool in its release after 2026-11-02, so new projects do not have it.
- **The project keeps the tool:** add the consumer to the declaration, as in
  `'dotgitignore@2.1.0 + @nestjs/cli@12.0.11 + @swc/cli@0.8.2 + @ts-morph/common@0.29.0 + nodemon@3.1.14 cannot use 11.0.1'`,
  and say in the entry's comment why the extra path is acceptable: dotgitignore compiles only the
  project's own `.gitignore` patterns, during a release.

### 4. When `RE-TEST` fails

The line says what moved. Re-test whether the fix works now. If it does, take it and delete the
entry from both `auditConfig.ignoreGhsas` and `auditConfig.unusableFixConsumers`. If it still does
not, update the declaration to what you assessed: consumers with their resolved versions, and the
rejected fix versions.

### 5. Hold `@iconify/vue` at 5.0.4

Every project that resolved its dependencies after 2026-11-02 has `@nuxt/icon` 2.6.2 next to
`@iconify/vue` 5.0.5, and that pair sends the browser to Iconify's public API: from the first
client-side navigation on, every icon outside the client bundle is fetched from
`api.iconify.design` instead of the app's `/_nuxt_icon` endpoint (nuxt/icon#571). Icons still
render, so nothing looks wrong; the network panel after a sign-in shows it. Where a CSP or a
firewall blocks that host, those icons are missing.

Check the pair, then copy the `'@iconify/vue': 5.0.4` entry **with its comment** from
`nuxt-base-template/pnpm-workspace.yaml` into the project's `overrides:` (in a monorepo the root
`pnpm-workspace.yaml`), together with `tests/unit/icon-endpoint-contract.test.ts`:

```bash
pnpm why @iconify/vue @nuxt/icon
pnpm install
pnpm exec vitest run tests/unit/icon-endpoint-contract.test.ts
```

The test runs both packages' own code and fails while they disagree. Remove the entry once a
`@nuxt/icon` release handles the new default and the test stays green without it.

### 6. Optional: the email field of the auth forms

On every auth page with a password field (in the template: `login.vue`, `register.vue`,
`setup.vue`), change the email field's `autocomplete: 'email'` to `autocomplete: 'username'`.
`username` names the identifier that belongs to the password, which is what the password manager
pairs with `current-password` and `new-password`; `email` only offers the address from the autofill
profile. Leave `forgot-password.vue` on `'email'`, and leave `type: 'email'` everywhere. Copy
`tests/unit/auth/autocomplete-contract.spec.ts` to keep it that way.

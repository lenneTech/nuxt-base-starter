# Migration Guide — 2.17.x → 2.18.0

Version 2.18.0 fixes a production lockout in the password-reset flow, closes the same
bug in e-mail verification, stops a development-only proxy from shipping in production
builds, and repairs a set of accessibility defects across the auth pages. Greenfield
projects created with a current `lt fullstack init` get all of it automatically.
**Forks of the 2.17.x starter** need the steps below — the first one is silent when
missed, and its symptom is that users cannot recover their accounts.

## What changed

| Area                     | Change                                                                                                                                                                                     |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Auth redirect origin** | New `app/utils/app-origin.ts` (`resolveAppOrigin`, `appUrl`). `runtimeConfig.public.siteUrl` is now declared, so `NUXT_PUBLIC_SITE_URL` actually reaches the app at runtime                |
| **Call sites**           | `forgot-password.vue` and `verify-email.vue` build their redirect through `appUrl()` instead of a template literal / a relative path                                                       |
| **New guard**            | `tests/unit/runtime-config-contract.test.ts` — every documented `NUXT_PUBLIC_*` must have a matching `runtimeConfig.public` key                                                            |
| **New E2E**              | `tests/e2e/auth-password-reset.spec.ts` — asserts the outgoing `redirectTo`                                                                                                                |
| **Dev proxy**            | `server/api/iam/[...path].ts` now 404s outside dev unless `apiProxy` is on, and only strips the `Secure` cookie flag over plain HTTP                                                       |
| **SEO config**           | `site.url` removed from `nuxt.config.ts` — `nuxt-site-config` reads the env var itself at higher priority, so the line could never win                                                     |
| **Route rules**          | `noindex` for `/auth/**`, `/app/**`, `/admin/**` alongside the existing robots.txt entries                                                                                                 |
| **a11y**                 | `htmlAttrs.lang: 'de'`; `<main>` + skip link in `layouts/slim.vue`; real `<h1>` on every auth page; `autocomplete` on every auth field; `aria-live` + focus move on the reset confirmation |
| **Auth UX**              | Reset errors render as a persistent inline alert routed through `translateError()`; the confirmation is non-enumerating; resend-with-cooldown and "use a different address" added          |
| **Page titles**          | Each auth page sets its own `useHead({ title })`                                                                                                                                           |
| **Test stub**            | `tests/unit/setup.ts` gives `window.location.href` a path so it is distinguishable from `origin`                                                                                           |

## Why the reset link broke

`nuxt.config.ts` never declared a `siteUrl` key under `runtimeConfig.public`. Nitro
applies `NUXT_PUBLIC_*` **only over keys that already exist**, so no matter how the
variable was set, `config.public.siteUrl` stayed `undefined`. The call site did:

```ts
redirectTo: `${config.public.siteUrl}/auth/reset-password`,
```

A template literal stringifies `undefined` rather than failing, so what actually went
over the wire was:

```json
{ "email": "…", "redirectTo": "undefined/auth/reset-password" }
```

Better Auth validates `redirectTo` against its trusted origins and answered **403
INVALID_REDIRECT_URL**. No mail was ever sent. The user saw a generic "Fehler" toast
that vanished after a few seconds, retried, and got the same result forever.

Two properties made this expensive: the failure was invisible in every environment
where nobody tried a password reset, and `.env.example` documented
`NUXT_PUBLIC_SITE_URL` correctly — so the variable _looked_ wired up. A test even
asserted it was documented. Nothing asserted it arrived.

## Prerequisite: nest-server 11.36.1 or newer

**Check this before anything else.** The steps below fix the frontend half of the flow.
The backend half was broken independently, and until 11.36.1 no
`emailAndPassword.sendResetPassword` hook was wired at all — so
`POST /iam/request-password-reset` answered `RESET_PASSWORD_DISABLED` and sent nothing,
no matter what the frontend supplied.

The two failures stack in a way that hides the second one: the origin-check middleware
runs before the endpoint handler, so a project with the old frontend sees only the 403.
Fix the frontend against an older backend and you trade `INVALID_REDIRECT_URL` for
`RESET_PASSWORD_DISABLED` — still no mail, still a locked-out user, but a different error
to chase.

```bash
# in the API project
pnpm add @lenne.tech/nest-server@latest   # 11.36.1 or newer
```

Two things change when the backend crosses that version:

- **Reset mail starts reaching real users.** The route goes live on first boot with no
  configuration. If your project deliberately has no self-service reset, turn it off
  explicitly with `betterAuth.emailAndPassword.passwordReset: false` rather than relying
  on it staying broken.
- **Check your rate limiting.** `betterAuth.rateLimit` is off unless the config object is
  present — `{}` is enough to arm it. Before 11.36.1 the mail-sending endpoint also
  slipped past the strict-endpoint list, so it ran on the full limit even when rate
  limiting looked configured.

While you are in the backend config, make sure `trustedOrigins` holds **exact origins and
no wildcard**. `redirectTo` is validated against it and the reset redirect carries a live
token; 11.36.1 warns at boot if it finds one.

## Upgrade steps

### 1. Declare the runtime config key (required)

In `nuxt.config.ts`, inside `runtimeConfig.public`:

```ts
runtimeConfig: {
  public: {
    // ...
    siteUrl: '',
  },
},
```

Without this the variable is inert, whatever you set in the environment.

### 2. Add the origin utility

Copy `app/utils/app-origin.ts` and `tests/unit/utils/app-origin.test.ts` from the
2.18.0 template. It depends on `hasControlCharacter` now being exported from
`app/utils/safe-redirect-target.ts` — export it there if your fork still has it
file-private.

### 3. Switch the call sites off interpolation

`app/pages/auth/forgot-password.vue`:

```diff
-      redirectTo: `${config.public.siteUrl}/auth/reset-password`,
+      redirectTo: appUrl('/auth/reset-password', config.public.siteUrl),
```

`app/pages/auth/verify-email.vue` — same class of bug, different mechanism. A relative
`callbackURL` is accepted by Better Auth and then redirected from the API's own origin,
so the user lands on `api.<host>/auth/verify-email`:

```diff
-        callbackURL: '/auth/verify-email',
+        callbackURL: appUrl('/auth/verify-email', runtimeConfig.public.siteUrl),
```

Grep your project for other `redirectTo` / `callbackURL` values before you finish —
anything relative or interpolated has the same defect.

### 4. Set the variable on every non-local stage (required)

```bash
NUXT_PUBLIC_SITE_URL=https://app.example.com
```

It is a **runtime** variable — `runtimeConfig.public.siteUrl` is applied when the
container boots, so one image works for every stage. Check that your deployment
actually passes it: an `lt-monorepo`-based `docker-compose.yml` may declare build args
but no `environment:` block for the app service, in which case nothing reaches the
container.

Use `NUXT_PUBLIC_SITE_URL`, **not** `NUXT_SITE_URL`. Both feed the SEO site config, but
only the public form also populates `runtimeConfig.public.siteUrl` — setting only the
latter gives you correct canonical URLs and a silently empty auth origin.

Unset is not fatal any more: the client falls back to the browser's own origin and
logs a console warning. That is right for a single-origin deployment and **wrong**
behind a proxy or vanity domain, where users then get links to the internal host.

### 5. Confirm the backend trusts the origin

Better Auth rejects any `redirectTo` whose origin is not in its `trustedOrigins`. Make
sure the app origin is registered on the API side (`nest-server` derives the list from
its configured origins, CORS `allowedOrigins`, passkey origins and `appUrl` — never
from the request). Avoid wildcards: reset links carry a one-time token.

### 6. Adopt the guard (recommended)

Copy `tests/unit/runtime-config-contract.test.ts`. It fails when a documented
`NUXT_PUBLIC_*` variable has no `runtimeConfig.public` key to land in — i.e. it would
have caught this bug before release. Add any module-owned variables of your project to
its `MODULE_OWNED` map with a reason.

### 7. Gate the dev proxy (recommended, security)

`server/api/iam/[...path].ts` rewrites `Set-Cookie` headers so cross-port cookies work
on localhost — including dropping the `Secure` flag. It was documented as
development-only but had no gate, and shipped in production builds. Add:

```ts
if (!import.meta.dev && !config.public.apiProxy) {
  throw createError({ statusCode: 404, statusMessage: 'Not Found' });
}
```

and make the `Secure` strip conditional on `getRequestProtocol(event) !== 'https'`.

### 8. Drop the redundant `site.url` (optional)

```diff
 site: {
   name: 'Your App',
-  url: process.env.NUXT_PUBLIC_SITE_URL,
 },
```

`nuxt-site-config` reads `NUXT_SITE_URL` / `NUXT_PUBLIC_SITE_URL` itself, at priority
`build` (−1) and `runtime` (0). A `url` in this block lands at `config` (−3) and can
never win, so the line only suggests an authoritative source that is not one.

### 9. Accessibility fixes (recommended)

These are independent of the redirect fix and each stands alone:

- `nuxt.config.ts` → `app.head.htmlAttrs: { lang: 'de' }`. The UI is German; without
  it screen readers use English phonetics (WCAG 3.1.1).
- `app/layouts/slim.vue` → wrap the slot in `<main>` and add a skip link. Every auth
  page uses this layout and had no landmark at all.
- Auth pages → `UAuthForm`'s `title` prop renders a `<div>`, not a heading. Use the
  `#title` slot to emit an `<h1>`, and promote state headings from `<h2>`.
- Auth form fields → add `autocomplete` (`email`, `current-password`, `new-password`,
  `name`). NuxtUI's `UInput` defaults to `"off"`, which suppresses password managers
  on exactly the forms that need them.
- Each auth page → `useHead({ title })`. All seven shared one browser title (WCAG 2.4.2).

## Verifying

1. `pnpm run check` — the new contract test and the resolver spec run in the unit suite.
2. On a real stage: request a password reset and **open the mail**. The link's origin must
   be your public hostname — not the container's internal address and not the API host.
   Then click it and confirm you land on the app's reset form.
3. Check the browser console on the forgot-password page. A
   `[app-origin] NUXT_PUBLIC_SITE_URL is unset or unusable` warning means the variable is
   not reaching the container.

Step 2 is the one that matters, and it is the only one that covers both halves — a mail
that arrives at the right host proves the frontend origin _and_ a backend new enough to
send it. If no mail arrives at all while the browser shows no error, check the API
response: `RESET_PASSWORD_DISABLED` means the backend is older than 11.36.1, not that this
migration failed.

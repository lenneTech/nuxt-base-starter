# Migration Guide — 2.31.x → 2.32.0

Version 2.32.0 makes uploads through `TusFileUpload` arrive. Before it, no upload with the
template's defaults ever reached the API, for four independent reasons (DEV-3595):

1. With `:multiple="false"` the component threw `newFiles.filter is not a function`: Nuxt UI writes a
   single `File` (and `null` after removal) to the v-model instead of `File[]`.
2. `TusFileUpload` forwarded its unset `endpoint` prop as `endpoint: undefined`, which erased the
   module default, so tus-js-client refused to start ("neither an endpoint or an upload URL is
   provided").
3. `ltExtensions.tus.defaultEndpoint: '/files/upload'` is relative and went to the APP origin, where
   nothing serves TUS: 404. nest-server serves TUS at `/tus` on the API.
4. In `nuxt dev`, tus-js-client's CommonJS dependency `url-parse` reached the browser unbundled, and
   the composable reported "tus-js-client is not installed".

And after a successful upload, the only identifier was the TUS upload URL. Its last segment is the
upload id, not the id of the stored file, so `/files/id/<it>` answered 404.

Projects created with a current `lt fullstack init` get all of it. **Existing projects do not**: the
files involved were copied when the project was created.

## What changed

| Area                | Change                                                                                                                                                                                                                                               |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **nuxt-extensions** | 1.18.6 → 1.19.0: a relative TUS endpoint now resolves against the API (`/api/tus` behind the dev proxy, `NUXT_PUBLIC_API_URL` + `/tus` otherwise), `endpoint: undefined` keeps the default, `url-parse` is pre-bundled in dev, `LtUploadItem.fileId` |
| **TUS endpoint**    | `ltExtensions.tus.defaultEndpoint` in `nuxt.config.ts`: `'/files/upload'` → `'/tus'`                                                                                                                                                                 |
| **TusFileUpload**   | Works with `:multiple="false"`; the watcher normalises the model through the new auto-imported util `toFileList` (`app/utils/to-file-list.ts`). The emitted `update:modelValue` is still `File[]`                                                    |
| **Tests**           | `tests/unit/components/tus-file-upload.test.ts` mounts the real component; `tests/unit/tus-endpoint-contract.test.ts` pins the endpoint. `typecheck:tests` runs `vue-tsc` instead of `tsc`, because a spec now imports a `.vue` file                 |

## Requirements

- **`fileId` needs `@lenne.tech/nest-server` 11.42.13 or later** on the API. It sends the stored
  file's id in the `X-File-Id` header of the response that completes the upload. Uploads themselves
  work with any version.
- The API serves TUS at `/tus` unless its `tus.path` says otherwise. If yours differs, use that path
  in step 3.

## Upgrade steps

Paths are relative to the app (`projects/app/` in a monorepo).

### 1. API: nest-server 11.42.13

Update `@lenne.tech/nest-server` to 11.42.13 (see its migration guide `11.42.12-to-11.42.13`). Skip
this only if the project never needs to know which file an upload produced.

### 2. API: own CORS options (only if the project has them)

Skip this if `main.ts` hands `buildCorsConfig()` to `enableCors()` unchanged, as the starter does.
A project that builds its own CORS options and lists `allowedHeaders` blocks every upload before
the first request reaches TUS:

`enableCors()` answers the preflight itself, so `CoreTusController` never sees it. tus-js-client
sends `Tus-Resumable`, `Upload-Length`, `Upload-Metadata` and `Upload-Offset`; when the preflight
response does not allow them, the browser drops the `POST`. `buildCorsConfig()` sets no
`allowedHeaders`, and without them the `cors` middleware allows whatever headers the browser asks
for.

Either drop `allowedHeaders` from the project's options, or add the headers `@tus/server` allows on
its own preflight:

```typescript
const TUS_HEADERS = [
  'Authorization',
  'Content-Type',
  'Location',
  'Tus-Extension',
  'Tus-Max-Size',
  'Tus-Resumable',
  'Tus-Version',
  'Upload-Concat',
  'Upload-Defer-Length',
  'Upload-Length',
  'Upload-Metadata',
  'Upload-Offset',
  'X-HTTP-Method-Override',
  'X-Requested-With',
  'X-Forwarded-Host',
  'X-Forwarded-Proto',
  'Forwarded',
];
```

If the options also set `methods`, they need `POST`, `HEAD`, `PATCH` and `DELETE`, the methods tus
uses. The `cors` default already contains them. `exposedHeaders` needs nothing: `@tus/server` sets
`Access-Control-Expose-Headers` on its own responses, `X-File-Id` included.

Whether the gap shows locally depends on the dev proxy. With `NUXT_PUBLIC_API_PROXY=true` (the
template's `.env.example`), uploads go to `/api/tus` on the app's own origin and the browser sends
no preflight, so everything works. `lt dev up` turns the proxy off: the app at
`https://<slug>.localhost` calls `https://api.<slug>.localhost`, and the gap shows locally just as
it does on a deployed stage.

### 3. App: nuxt-extensions 1.19.0 and the endpoint — together

Check the mode first: `test -f app/core/VENDOR.md`.

- **npm mode** (no `VENDOR.md`):

  ```bash
  pnpm add @lenne.tech/nuxt-extensions@1.19.0
  ```

- **vendor mode** (`app/core/VENDOR.md` exists): do **not** run `pnpm add`. The app loads the module
  from `app/core/`, so an npm install changes nothing at runtime, and the 1.18.x core keeps all three
  library defects. Update the vendored core to 1.19.0 with `/lt-dev:frontend:update-nuxt-extensions-core`
  and check that `VENDOR.md` then reads `Baseline-Version: 1.19.0`.

Then, in both modes:

```diff
  ltExtensions: {
    tus: {
-     defaultEndpoint: '/files/upload',
+     defaultEndpoint: '/tus',
      defaultChunkSize: 5 * 1024 * 1024,
    },
  },
```

**Do not take only the package update.** With 1.19.0, `'/files/upload'` resolves to
`<API>/files/upload`, which in a nest-server API is the multipart route, not TUS. Nothing fails at
build time; uploads just never arrive.

Two setups need more than this; nuxt-extensions' guide `1.18.x-to-1.19.0` covers them: a project
that routes uploads through its own same-origin proxy (set `tus.resolveAgainstApi: false`), and an
endpoint that carries the dev-proxy prefix itself (`'/api/files/upload'`, drop the `/api`).

### 4. TusFileUpload (if the project still has the template's component)

Copy `app/utils/to-file-list.ts` from the template, then change the watcher in
`app/components/Upload/TusFileUpload.vue`:

```diff
- const files = ref<File[]>([]);
+ // UFileUpload liefert bei `multiple: false` eine einzelne File bzw. null statt File[]
+ const files = ref<File | File[] | null>([]);

  watch(
    files,
-   (newFiles, oldFiles) => {
-     const addedFiles = newFiles.filter((f) => !oldFiles?.includes(f));
+   (newValue, oldValue) => {
+     const newFiles = toFileList(newValue);
+     const oldFiles = toFileList(oldValue);
+     const addedFiles = newFiles.filter((f) => !oldFiles.includes(f));
```

A project that modified the component: apply the same normalisation wherever it reads the
`UFileUpload` model as an array.

### 5. Reference files by `fileId`

```typescript
// before: item.url?.split('/').pop() — the TUS upload id, /files/id/<it> answers 404
const fileId = item.fileId;
```

`fileId` is optional: it is `undefined` against an API older than 11.42.13, and when the API
overrides `CoreTusService.onUploadComplete()` without calling `super`. Do not fall back to the last
segment of `url` then.

### 6. Tests (recommended)

Copy `tests/unit/components/tus-file-upload.test.ts` and `tests/unit/tus-endpoint-contract.test.ts`.
The contract test checks the version the app actually runs: the `Baseline-Version` in
`app/core/VENDOR.md` in vendor mode, the npm dependency otherwise.
The component spec imports a `.vue` file, which plain `tsc` cannot resolve, so switch the tests half
of the type gate in `package.json`:

```diff
- "typecheck:tests": "… nuxt prepare && tsc --noEmit -p tsconfig.tests.check.json && …",
+ "typecheck:tests": "… nuxt prepare && vue-tsc --noEmit -p tsconfig.tests.check.json && …",
```

`vue-tsc` is already a devDependency (`pnpm run typecheck` uses it).

## Verify

Sign in, upload a file through a `TusFileUpload`, and watch the network panel:

- `POST <API>/tus` (`/api/tus` behind the dev proxy) answers 201, the following `PATCH` 204.
- The last `PATCH` carries `X-File-Id` (nest-server 11.42.13+), and the component's `success` event
  delivers it as `item.fileId`.
- `GET <API>/files/id/<fileId>` answers 200.

Repeat the upload once where app and API have different origins (`lt dev up` or a deployed stage):
the `OPTIONS` preflight to `<API>/tus` must answer 204 with `Tus-Resumable` among the allowed
headers (step 2).

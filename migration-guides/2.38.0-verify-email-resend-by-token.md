# Migration Guide — 2.37.0 → 2.38.0: "send a new e-mail" by token, and E2E tokens from nest-server 12.6.0

From nest-server 12.6.0 on, the link in the verification mail carries the token only, sealed, and no
e-mail address. Two things in a project depend on that address or on the old token.

- **The page.** `/auth/verify-email` offers "send a new e-mail" for a refused link only when it knows
  the address. Until 12.6.0 the link brought it as `&email=`. With a 12.6.0 link a visitor whose
  link expired gets no button and has to start over at the sign-up or the login.
- **The E2E helper.** `findVerificationToken()` identified a token by the address in its payload.
  The sealed token has no readable payload, so every spec that confirms an address fails with
  "Verification token not found in server logs" once the API runs 12.6.0.

2.38.0 sends a refused link's token to `POST /iam/resend-verification-email` while `GET /iam/features`
reports `resendVerificationByToken`. The API mails the address the token belongs to and answers it
masked (`k***@example.com`), so nobody types the address and it never travels. Without the flag the
page behaves as before, and without any address it asks for one in a field. The helper reads both
log formats.

| Project                                   | What to do                                                       |
| ----------------------------------------- | ---------------------------------------------------------------- |
| Moves to nest-server 12.6.0 or newer      | Steps 1 and 2, **before** the API update; step 3 is optional     |
| Stays on an older nest-server for now     | Steps 1 and 2 are safe already: without the flag nothing changes |
| Has no E2E suite with e-mail verification | Step 2 only                                                      |

## What changed

| Area           | Change                                                                                                                                                                                                                                        |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Page**       | `app/pages/auth/verify-email.vue` reads `resendVerificationByToken` from `/iam/features` and sends a refused link's token for a new mail; shows the masked address; shows `429 LTNS_0020` translated; asks for the address when it knows none |
| **Memory**     | `app/utils/verify-email-memory.ts` keeps the refused token in the history entry (`deadToken`), so a reload still offers the new mail. `verifyEmailState(email, true)` is now `verifyEmailState(email, { verified: true })`                    |
| **E2E helper** | `tests/e2e/helpers/auth-backend.ts`: `findVerificationToken()` matches the `UserKey` of the 12.6.0 log line, and the JWT payload of older lines; `Features` gains `resendVerificationByToken`, off by default                                 |
| **Tests**      | New `tests/unit/pages/auth-verify-email.test.ts` (every way of the resend), extended `tests/unit/e2e-auth-backend.test.ts`, `tests/unit/utils/verify-email-memory.test.ts` and `tests/e2e/auth-verify-email-url.spec.ts`                      |

## Upgrade steps (existing project)

In an `lt fullstack` monorepo, all steps happen in `projects/app/`.

### 1. Take over the E2E helper, before the API goes to 12.6.0

Copy `tests/e2e/helpers/auth-backend.ts` and `tests/unit/e2e-auth-backend.test.ts` from the template.
A project that changed its helper takes over:

- `userKey()` and `jwtEmail()`, and `findVerificationToken()` as a whole,
- the `import { createHash } from 'node:crypto'` at the top,
- `resendVerificationByToken` in the `Features` interface and `resendVerificationByToken: false` in
  `DEFAULT_FEATURES`.

The order matters: an API on 12.6.0 with the old helper turns every spec that confirms an address
red. 12.6.0 prints the log line only in the `local`, `ci` and `e2e` environments; the CI start of
nest-server-starter (`start:e2e:dist`) is one of them.

```bash
pnpm exec vitest run tests/unit/e2e-auth-backend.test.ts
```

### 2. Take over the page and its memory

Copy `app/pages/auth/verify-email.vue`, `app/utils/verify-email-memory.ts` **and**
`tests/unit/utils/verify-email-memory.test.ts`. The test is not optional: the 2.37.0 version of it
expects the entry without `deadToken` and fails against the new file.

A project that changed its page takes over:

- the refs `resendByToken`, `deadToken`, `maskedEmail`, `addressForm` and the schema `addressSchema`,
- the computeds `resendMode` and `resendLabel`,
- in `verifyEmailWithToken()`: keeping the refused token (`linkRefused`, `rememberPage()`),
- the functions `resendWithToken()`, `resendToTypedAddress()`, `resendToAddress()` and
  `rememberPage()` (it replaces `rememberVerified()`),
- in `onMounted`: `resendByToken` from the features and the branch for `remembered.deadToken`,
- in the template: the shared block for the refused and the waiting state, with the address field.

A project that calls `verifyEmailState(email, true)` elsewhere changes it to
`verifyEmailState(email, { verified: true })`; `pnpm run typecheck` names every place.

```bash
pnpm exec vitest run tests/unit/utils/verify-email-memory.test.ts
pnpm run typecheck
```

### 3. Optional: take over the tests of the page

Copy `tests/unit/pages/auth-verify-email.test.ts` and `tests/e2e/auth-verify-email-url.spec.ts`. The
unit test runs in every project. The E2E spec runs against a real API, against nest-server 12.6.0
and older ones alike.

Vendor mode: change the spec's import `from '@lenne.tech/nuxt-extensions/testing'` to
`from '../../app/core/runtime/testing'`, as in your other specs. The CLI rewrote those when it
vendored the core; a file copied later keeps the npm import, and `pnpm run typecheck:tests` fails on
it because the package is gone.

## Check it

Against an API on nest-server 12.6.0, open `/auth/verify-email?token=refused` and choose "Neue E-Mail
senden". The browser's network panel shows `POST /iam/resend-verification-email` with
`{ "token": "refused" }`, the answer `{ "email": null, "success": true }`, and the page then asks for
the address. With an expired link from a real mail the page shows the masked address instead, and
the new mail arrives. Against an older API the page sends to the address of the link as before.

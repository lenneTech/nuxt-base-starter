# 2.19.0 — `config.public.*` types as `unknown` in vendor-mode projects

**Who this affects:** projects whose frontend is in **vendor mode** and that were
generated or converted before lt CLI 1.43.0. npm-mode projects were never affected.

**Do I need to do anything?** Run one command in `projects/app`:

```bash
grep -rn "declare module '@nuxt/schema'" app/core/
```

A match means yes. No output means no — nothing to do, and nothing to read below.

---

## The symptom

`pnpm run typecheck` fails on code that is correct:

```
app/utils/app-origin.ts(5,22): error TS2345:
  Argument of type 'unknown' is not assignable to parameter of type 'string'.
```

Any `useRuntimeConfig().public.x` read produces it. `config.public.siteUrl` is
declared `string` and infers as `unknown`.

## The fix

Delete the two `declare module '…/schema'` blocks at the end of
`app/core/runtime/types/module.ts`:

```ts
declare module 'nuxt/schema' {
  interface PublicRuntimeConfig extends LtExtensionsPublicRuntimeConfig {}
}

declare module '@nuxt/schema' {
  interface PublicRuntimeConfig extends LtExtensionsPublicRuntimeConfig {}
}
```

Then:

```bash
rm -rf .nuxt .nuxt-check && pnpm run typecheck
```

**Nothing is lost by deleting them.** `ltExtensions` does not reach the consumer
through those blocks — the module sets its runtime-config defaults at build time, so
Nuxt writes the whole shape into the generated types either way. Verified after
removal: `config.public.ltExtensions.auth.enabled` is `boolean`,
`.auth.basePath` is `string`, `config.public.siteUrl` is `string`, and the type gate
reports zero errors.

## Why it happened

`nuxt/schema` is a re-export of `@nuxt/schema`. Augmenting `PublicRuntimeConfig`
under both names therefore decorates **one** interface twice.

While the file lives in `node_modules` that is inert — nothing imports it, so it never
enters the consumer's TypeScript program. Vendoring copies it to `app/core/`, where the
project's own `include` picks it up unconditionally. It then closes a cycle with Nuxt's
generated `interface PublicRuntimeConfig extends UserPublicRuntimeConfig`:

```
.nuxt/types/runtime-config.d.ts: error TS2310:
  Type 'PublicRuntimeConfig' recursively references itself as a base type.
```

Every member of an interface in that state resolves to `unknown`.

## Why nobody could see the cause

Nuxt sets `skipLibCheck: true`, which suppresses TS2310 — it is reported in a `.d.ts`.
So the cause is invisible and only the consequence shows, at a call site that is not
wrong. To see it:

```bash
npx vue-tsc --noEmit -p .nuxt-check/tsconfig.json --skipLibCheck false | grep TS2310
```

The `grep` matters: without it the command prints roughly 500 unrelated third-party
`.d.ts` errors even on a perfectly healthy project. Two `ViteOptions` TS2310s are
normal — the one that matters names `PublicRuntimeConfig`.

For the record, this was previously written up in this repo as "vendor mode does not
emit the `declare module 'nuxt/schema'` block". That was wrong. The block **is**
emitted, byte-identically in both modes — measured by converting the template and
diffing the two generated files.

## Keeping it fixed

New conversions strip the blocks automatically (`lt fullstack init`,
`lt frontend convert-mode`) and leave a comment in their place explaining why.

**Re-check after every vendored-core update.** `/lt-dev:frontend:update-nuxt-extensions-core`
copies upstream files verbatim, so a sync that touches
`app/core/runtime/types/module.ts` brings the blocks back — and the failure is silent
until someone runs the type gate. The updater agent carries this as a documented edge
case, but the grep at the top of this guide is the check that does not depend on
anyone remembering.

# Migration Guide: the login page offers the sign-in methods `/iam/features` reports

From nest-server 12.11.0 on, `GET /iam/features` reports `emailAndPassword`. It is `false` for an API
that signs in through social providers alone (`betterAuth.emailAndPassword.enabled: false`), and such an
API then reports `passkey: false` and `twoFactor: false` as well, unless it keeps a factor deliberately.
Until now the login page showed the e-mail and password form, "Passwort vergessen?", "Registrieren"
and the passkey button whatever the API reported. On a provider-only API every one of them leads to an
error.

The login page now follows the features:

- `emailAndPassword: false`: no form, no "Passwort vergessen?", no "Registrieren". `/auth/register`
  sends the visitor to the login with a toast; with sign-up open, the account comes with the first
  sign-in through a provider.
- `passkey: false`: no passkey button. This also holds for an older API with passkeys switched off,
  where the button could only fail.
- No method left at all: the hint "Anmeldung nicht möglich" instead of an empty card.
- The page fetches `/iam/features` during SSR, so the server HTML already shows the right methods and
  nothing appears or disappears after load. This also covers the provider buttons, which before were
  added only on the client.

Only an explicit `false` takes a method away. An API before 12.11.0 does not report `emailAndPassword`,
and the form stays.

| Project                                                                     | What to do                  |
| --------------------------------------------------------------------------- | --------------------------- |
| Signs in through providers alone, or will (API on nest-server 12.11.0+)     | Steps 1 and 2, then 3       |
| Has passkeys switched off in the API                                        | Step 1                      |
| Carries `tests/unit/pages/auth-login-social.test.ts` or wants the E2E check | Step 3, optional            |
| Any other                                                                   | Nothing; step 1 if you like |

No dependency changes. The template's pages work with every nuxt-extensions 4.x.

## Upgrade steps (existing project)

In an `lt fullstack` monorepo, the steps happen in `projects/app/`.

### 1. `app/pages/auth/login.vue`

Take over the file if yours is the starter's. Otherwise apply the changes by hand. In the script,
after `featuresArrived`:

```ts
// What /iam/features answered the server, for the first render; the payload brings it to the browser.
const serverFeatures = useState<null | Record<string, unknown>>('login-server-features', () => null);
if (import.meta.server) {
  try {
    serverFeatures.value = await $fetch<Record<string, unknown>>(`${getLtApiBase()}/features`);
  } catch {
    serverFeatures.value = null;
  }
}

// The browser's answer once it is there, the server's until then.
const signInFeatures = computed<Record<string, unknown>>(() => (featuresArrived.value ? features.value : (serverFeatures.value ?? {})));

const passwordSignIn = computed(() => signInFeatures.value.emailAndPassword !== false);
const passkeySignIn = computed(() => signInFeatures.value.passkey !== false);
const noSignInMethod = computed(() => !passwordSignIn.value && !passkeySignIn.value && socialButtons.value.length === 0);
```

The provider buttons follow `signInFeatures` as well
(`socialProvidersOf(signInFeatures.value)`); the silent attempt keeps reading `features`, the browser's
answer. A page without social buttons has no `socialButtons`; use `[]` there.

Two traps:

- **Not `useLtAuth().fetchFeatures()` on the server**, as `register.vue` does. It marks the features as
  fetched, the browser never asks again, and an E2E spec that answers `/iam/features` in the browser
  (the starter's `auth-social-sign-in.spec.ts`) fails against a running API.
- **Not in `onServerPrefetch`.** A call after the first `await` runs there without the Nuxt instance,
  and `nuxt dev` logs `NUXT_E1001` on every server render of the page.

In the template:

- `UAuthForm` gets `:fields="passwordSignIn ? fields : []"`. Without fields it renders no form and no
  submit button, and "Passwort vergessen?" goes with the password field.
- The separator `oder` only with `v-if="passwordSignIn && (passkeySignIn || socialButtons.length > 0)"`.
- The passkey button gets `v-if="passkeySignIn"`.
- After it, the hint:

  ```vue
  <UAlert
    v-if="noSignInMethod"
    color="warning"
    variant="subtle"
    icon="i-lucide-circle-alert"
    title="Anmeldung nicht möglich"
    description="Für diese Anwendung ist derzeit keine Anmeldemethode eingerichtet. Bitte wende dich an die Betreiber der Anwendung."
  />
  ```

- The paragraph with "Registrieren" gets `v-if="passwordSignIn && signInFeatures.signUpEnabled !== false"`.

### 2. `app/pages/auth/register.vue`

The watcher that sends the visitor to the login on `signUpEnabled === false` watches
`emailAndPassword` too:

```ts
watch(
  [() => features.value.signUpEnabled, () => features.value.emailAndPassword],
  ([signUpEnabled, emailAndPassword]) => {
    if (import.meta.server) {
      return;
    }
    if (signUpEnabled === false || emailAndPassword === false) {
      toast.add({
        color: 'warning',
        description:
          signUpEnabled === false
            ? 'Die Registrierung ist derzeit deaktiviert.'
            : 'Eine Registrierung mit E-Mail und Passwort ist hier nicht möglich. Bitte melde dich über die Anmeldeseite an.',
        title: 'Registrierung nicht verfügbar',
      });
      navigateTo('/auth/login', { replace: true });
    }
  },
  { immediate: true },
);
```

Keep the redirect on the client. A redirect from the server is a bare 302 without a payload, and the
toast would be lost. `replace: true` is new for both cases: pushed, the redirect left `/auth/register`
in the history, "Back" returned there, the page sent the visitor to the login again, and every round
added a toast (measured 2026-11-25).

### 3. Optional: the tests

- `tests/unit/pages/auth-login-social.test.ts`: take the file over. The `await` makes the page's setup
  asynchronous, so the harness now mounts it inside `<Suspense>`, as Nuxt does; without that the
  page renders nothing and nearly every test of the file fails. It also stubs `useState`, `$fetch` and
  `getLtApiBase`, takes `serverFeatures` (the server's answer in the payload), and its `UAuthForm` stub
  renders the form only while there are fields, as Nuxt UI does.
- `tests/e2e/auth-sign-in-methods.spec.ts`: copy it, and add `emailAndPassword: boolean` to `Features`
  and `emailAndPassword: true` to `DEFAULT_FEATURES` in `tests/e2e/helpers/auth-backend.ts`. Without the
  field `pnpm run typecheck:tests` fails with `TS2339`. In vendor mode change the spec's import
  `from '@lenne.tech/nuxt-extensions/testing'` to `from '../../app/core/runtime/testing'`. The spec
  needs `app/utils/social-sign-in.ts` (starter 4.0.3).

  Against an API as nest-server-starter ships it, the spec checks that the form stays. The
  provider-only case needs an API started with `NSC__BETTER_AUTH__EMAIL_AND_PASSWORD__ENABLED=false`
  and a provider (`NSC__BETTER_AUTH__SOCIAL_PROVIDERS__GITHUB__CLIENT_ID` and `__CLIENT_SECRET`, any
  value) and the spec run with `E2E_SIGN_IN_CASE=providers-only`. Without that variable, the
  provider-only checks skip.

## Check it

```bash
pnpm run check
```

With the API signing in through a provider alone, open `/auth/login`: only the provider buttons
show, already with JavaScript off. `/auth/register` goes to the login with "Registrierung nicht
verfügbar".

# Migration Guide — 2.34.1 → 2.35.0: Plausible and URLs with secrets

Every project built from this template sent secrets to its analytics host, without any opt-in.
`@nuxtjs/plausible` is on by default and falls back to `plausible.io` when
`NUXT_PLAUSIBLE_API_URL` is not set at build time. Its tracker reports `location.href` the moment it
starts, before a page can strip anything, and repeats that URL in the `engagement` event when the
page is left.

Measured on a built server with a real hostname:

- `/auth/reset-password?token=…` sent the live token twice. A reset token can set the password for
  as long as it is valid.
- `/auth/verify-email?token=…&email=…` sent the token and the e-mail address.
- The address also went out on `/auth/verify-email?email=…`, where sign-up and sign-in send people.
- `document.referrer` carried the same URL to the next page, as soon as a link from one of these
  pages opened in a new tab or a click came before hydration.

**Steps 1 to 3 are required for every project that has `@nuxtjs/plausible`**, whether or not it uses
Plausible on purpose. They belong together, and a partial update fails without a sign:

| Done                  | Result                                                          |
| --------------------- | --------------------------------------------------------------- |
| Step 1 without step 2 | The token still goes out first, and every pageview counts twice |
| Step 2 without step 1 | No pageviews at all, and no error                               |

Local development and E2E show neither: the tracker ignores `localhost` and automated browsers.

## What changed

| Area                 | Change                                                                                  |
| -------------------- | --------------------------------------------------------------------------------------- |
| **Pageviews**        | Sent by `app/plugins/plausible-pageviews.client.ts`, with a URL reduced by an allowlist |
| **Plausible config** | `plausible.autoPageviews: false`                                                        |
| **Referrer-Policy**  | `strict-origin` instead of `strict-origin-when-cross-origin`                            |

The URL keeps `utm_*`, `ref`, `source`, `gclid` and `msclkid`, which is what Plausible reports on.
Everything else in the query and the fragment is dropped.

## Steps

1. Copy `app/utils/analytics-url.ts` and `app/plugins/plausible-pageviews.client.ts` from the
   template.
2. In `nuxt.config.ts`, set `autoPageviews: false` in the `plausible` block.
3. In `server/utils/security-headers.ts`, set `'Referrer-Policy': 'strict-origin'`. A project that
   sets the header elsewhere, such as in a reverse proxy, changes it there. Same-origin requests now
   send only the origin as referrer; cross-origin behaviour does not change.
4. Search the project for `useTrackPageview`, `useTrackEvent`, `$plausible` and `window.plausible`.
   A call without a `url` reports `location.href`, so pass `url: analyticsUrl(window.location.href)`.
5. A project with `plausible.hashMode: true` needs its own decision: `analyticsUrl` drops the
   fragment, and only a new path counts as a pageview.
6. Optional: copy `tests/unit/utils/analytics-url.test.ts` and
   `tests/unit/plugins/plausible-pageviews.test.ts`. The first imports
   `@plausible-analytics/tracker` directly, so the project needs that dependency (2.34.0, step 7).

A project that does not use Plausible at all can set `plausible: { enabled: false }` instead of
steps 1 and 2. Step 3 still applies.

## Check it

Open a reset link on a deployed stage and watch the requests to `/api/event` in the browser's
network panel. `u` must not contain `token`, and `r` must hold at most the origin. On `localhost`
nothing is sent at all, so that proves nothing.

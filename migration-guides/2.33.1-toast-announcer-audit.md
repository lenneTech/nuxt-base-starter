# Migration Guide — 2.33.0 → 2.33.1

Version 2.33.1 makes toasts audible to screen readers again, and gets `pnpm run check` green again
after two audit changes on 2026-10-28.

- **Toasts.** Since reka-ui 2.10.0 the toast announcer, the element carrying `role="alert"` and
  `aria-live`, sits inside an `aria-hidden="true"` wrapper. Screen readers never announce it, while
  the toast itself still renders visibly. reka-ui 2.10.1 came in with `@nuxt/ui` 4.10.0, so every
  project created from template 2.13.2 (2026-07-18) onwards is affected. Upstream has merged the fix
  (unovue/reka-ui#3050, 2026-10-26) but not released it. The template backports it as a one-line
  patch.
- **deepmerge.** `pnpm audit` reports GHSA-gcqx-w48m-w2h4 (low) since 2026-10-28, and no fixed
  deepmerge exists. That alone turns `check` red in every project. The template suppresses it with a
  reason.
- **node-forge.** 1.4.1 (2026-10-27) fixes GHSA-86w9-cpqp-85rv, which the template had suppressed
  since 2.28.0. A fresh resolve now gets 1.4.1, and `check-suppressions.mjs` then fails on the
  orphaned entry as `NOT IN TREE`. The template resolves 1.4.2, which also fixes a regression of
  1.4.1, and drops the entry.
- **Dev console.** `nuxt dev` no longer prints three `[unhead]` SEO warnings on every page without
  its own description.
- **Dependencies.** nuxt 4.6.3 closes GHSA-9v7c-q64q-vv33 (medium): dot segments in the request path
  bypass `server/middleware` path checks and server route rules on page routes. It is published in
  the nuxt repository only, so `pnpm audit` does not report 4.6.0 to 4.6.2. Also
  `@lenne.tech/nuxt-extensions` 1.20.1, pnpm 11.28.9 and the `postcss-selector-parser` override back
  in typography's own major.

Projects created with a current `lt fullstack init` get all of it. **Existing projects do not**: the
files involved were copied when the project was created. Step 2 is required right away, because
`pnpm audit` fails without it. Step 6 is a security update and belongs in the same change. Step 3 is
required as soon as the lockfile resolves node-forge 1.4.1 or later. Step 1 is not enforced by any
gate, and it is the one that matters to users.

## Upgrade steps (existing project)

In an `lt fullstack` monorepo, `pnpm-workspace.yaml` and `patches/` live at the **root**: pnpm reads
`auditConfig` and `patchedDependencies` only there.

### 1. Backport the reka-ui toast fix

Check which reka-ui the project resolves:

```bash
pnpm why -r reka-ui
```

The fix only works on reka-ui 2.11.0 (`@nuxt/ui` 4.12.0). On a 2.10.x version (`@nuxt/ui` 4.10.0 to
4.11.3), raise `@nuxt/ui` to 4.12.0 first, together with the `'@nuxt/ui@<4.8.1'` override target (see
2.33.0). Do not write your own patch for 2.10.x: there `VisuallyHidden` sets `aria-hidden="true"` for
the default `focusable` feature as well, so removing `feature: "fully-hidden"` leaves the announcer
just as hidden. Only 2.11.0 limits `aria-hidden` to `fully-hidden`.

On 2.11.0, copy `patches/reka-ui@2.11.0.patch` and the `patchedDependencies` block, comment
included, from the template's `pnpm-workspace.yaml`, then run `pnpm install`. Verify the result with
the template's `tests/unit/toast-live-region.test.ts`, or in an E2E spec after an action that shows a
toast:

```ts
await expect(page.getByRole('alert').filter({ hasText: '<toast title>' })).toBeVisible();
```

Without the fix, Playwright finds only a hidden node there.

A Dockerfile that copies a curated file list instead of the template's
`{ [ ! -d /tmp/src/patches ] || cp -rf /tmp/src/patches /app/; }` needs `COPY patches/ ./patches/`
before `pnpm install`. Otherwise `--frozen-lockfile` stops with `ENOENT` inside the image.

### 2. Suppress the deepmerge advisory

Copy the `GHSA-gcqx-w48m-w2h4` entry, comment included, into `auditConfig.ignoreGhsas` of
`pnpm-workspace.yaml`. Check that deepmerge reaches your project only through build tooling:

```bash
pnpm why -r deepmerge
```

In the template the only path is nitropack > `@rollup/plugin-node-resolve`, which merges a hard-coded
constant with it. In a monorepo `@nestjs/cli` > `fork-ts-checker-webpack-plugin` adds a second
path, also build-time only. Any other consumer needs its own assessment before you suppress.

### 3. Move node-forge to 1.4.2 and drop its suppression

`pnpm update node-forge` leaves a transitive 1.4.0 in place, with or without `--depth Infinity`
(measured with pnpm 11.28.8). What works is a temporary override:

```bash
# 1. pnpm-workspace.yaml, under overrides:   node-forge: 1.4.2
pnpm install
# 2. remove that line again
pnpm install
pnpm why -r node-forge    # 1.4.2, and nothing older
```

Then delete the `GHSA-86w9-cpqp-85rv` entry from `auditConfig.ignoreGhsas`. `pnpm audit` stays
clean without it. 1.4.1 closes the advisory too, but breaks `pem.decode()` for Buffer input; 1.4.2
fixes that. listhen, the only consumer, passes strings and is affected by neither.

Projects created from template 2.28.0 or later carry `tests/unit/check-suppressions.test.ts`, and two
of its tests pin exactly what this step removes: `finds node-forge 1.4.0 in the template's real
lockfile` and `lists this template's own entry` (which expects `GHSA-86w9-cpqp-85rv`). Both turn red.
Replace those two `it(…)` blocks with the template's `reads the template's real lockfile` and
`lists exactly the entries the real pnpm-workspace.yaml declares`. They check that `nuxt` resolves
and that the parser agrees with the file, so they no longer break when an entry comes or goes.
Replace only these two blocks, not the whole file: the rest of the file has to match your copy of
`scripts/check-suppressions.mjs`.

### 4. Optional: login and register error toasts that say something

With the announcer audible again, a weakness of two toasts becomes louder. When sign-in or sign-up
fails without an error message, which is what an unreachable API or a proxy 5xx produces,
`login.vue` and `register.vue` used the title text as the description, so the toast and the screen
reader said "Anmeldung fehlgeschlagen" twice. Take the `if (result.error)` block of
`app/pages/auth/login.vue` and the `if (signUpResult.error)` block of `app/pages/auth/register.vue`
from the template. Both now check the message before translating it
(`errorMessage ? translateError(errorMessage) : '… ist gerade nicht möglich. Bitte versuche es später erneut.'`),
and the login page checks it before testing for `LTNS_0023`. The new `describe` block at the end of
`tests/unit/auth/auth-pages-translate-errors.spec.ts` keeps the pattern from coming back.

### 5. Optional: a clean dev console

nuxt-seo-utils runs unhead's validator in the browser during `nuxt dev`. On every page without its
own description it printed three warnings, and two of them are wrong there:

- `twitter:card is deprecated`: unhead's own meta inference adds the tag that its own validator
  flags (unjs/unhead#842).
- `Meta tag "og:description" has empty content` and
  `Page is missing a meta description and is indexable by search engines`: the inferred
  `og:description` is empty without a description, and the validator checks before empty tags are
  dropped. "Indexable" also fires on `noindex` pages, because `@nuxtjs/robots` sets its meta tag on
  the server only and the validator reads the client head.

Add the top-level `seo` block and `site.description` from the template's `nuxt.config.ts`, with your
own product sentence instead of the template's. `seo.automaticTwitterTags` needs nuxt-seo-utils
8.5.0 or later (`pnpm why -r nuxt-seo-utils`); on an older version the key does nothing, so update
`@nuxtjs/seo` first. Keep, or add, an own `useSeoMeta({ description })` on every public page, and copy
`tests/unit/seo-dev-console-contract.test.ts` so the shared fallback cannot hide a forgotten one.
Turning validation off altogether (`unhead: { vite: { validate: false } }`) would also silence the
checks worth having, such as a relative `og:url` or an unresolved `%` placeholder.

### 6. nuxt 4.6.3, nuxt-extensions 1.20.1, pnpm 11.28.9

In `package.json` of the app (exact versions, like the template):

```json
"@lenne.tech/nuxt-extensions": "1.20.1",
"nuxt": "4.6.3"
```

Copy the `packageManager` line, hash included, from the template into every `package.json` that
carries one (in an `lt fullstack` monorepo also the root and the api). Docker and CI derive pnpm from
that field. Then run `pnpm install` and check that no 4.6.2 copy is left:

```bash
pnpm why -r nuxt @nuxt/nitro-server    # 4.6.3 only
pnpm why -r @nuxt/kit @nuxt/schema     # an in-place bump may leave 4.6.2 behind
```

The 4.6.2 copies of `@nuxt/kit` and `@nuxt/schema` carry no advisory, so removing them is hygiene.
If you want to remove them, add the temporary overrides `'@nuxt/kit@4.6.2': 4.6.3` and
`'@nuxt/schema@4.6.2': 4.6.3`, run `pnpm install`, remove both, and run `pnpm install` again.

Libraries that emit declaration files may hit TS2742 on `defineNuxtPlugin()` under nuxt 4.6.3
(nuxt-extensions did). The fix there is `}) as Plugin & ObjectPlugin` with
`import type { ObjectPlugin, Plugin } from '#app'`. An app does not emit declarations, and the
template's typecheck passes unchanged.

If the project carries the override `'postcss-selector-parser@<7.1.6': 7.1.7`, replace it with
`'postcss-selector-parser@<6.1.5': 6.1.5`, comment included, from the template's
`pnpm-workspace.yaml`, then run `pnpm install` and `pnpm audit`.

## Removing the patch later

Delete `patches/reka-ui@2.11.0.patch` and the `patchedDependencies` entry together once `@nuxt/ui`
resolves a reka-ui release that contains unovue/reka-ui#3050. pnpm insists on it: once reka-ui moves
off 2.11.0, every install stops with `ERR_PNPM_UNUSED_PATCH` until both are gone. Keep the test.
